### Фаза 1 (P0). Размер элемента очереди команд — блокер

**Места:** `SsvcCommandsQueue.h` (`COMMAND_QUEUE_ITEM_SIZE`, `COMMAND_QUEUE_LENGTH`), `SsvcCommandsQueue.cpp` (`SsvcCommandsQueue()`, `pushCommandInQueue`, `commandProcessorTask`).

**Проблема:** очередь создана с `uxItemSize = sizeof(SsvcCommand)`, а `xQueueSend`/`xQueueReceive` получают `&cmd`, где `cmd` — указатель. FreeRTOS копирует `uxItemSize` байт по этому адресу: чтение/запись за пределами переменной указателя, риск повреждения стека задачи.

**Шаги**
1. `COMMAND_QUEUE_ITEM_SIZE` → `sizeof(SsvcCommand*)`.
2. Проверить, что обе стороны обмена используют адрес указателя: `xQueueSend(command_queue, &cmd, …)` и `xQueueReceive(self->command_queue, &cmd, …)`; привести к единому виду.
3. Не переводить очередь на передачу `SsvcCommand` по значению: внутри `std::string`, а байтовое копирование RTOS не вызывает конструктор копирования (владение — по указателю).
4. Проверить жизненный цикл владения: `new SsvcCommand()` → `delete cmd` при отказе постановки и после обработки; ветка повторных попыток (`while (cmd->attempt_count != 0)`) не должна оставлять объект ни живым, ни удалённым дважды.
5. Проверить, что при `command_queue == nullptr` воркер не работает с нулевым дескриптором (см. Фазу 8).

**Критерий:** при `uxQueueMessagesWaiting`/`uxQueueSpacesAvailable` и обмене командами нет обращений за границы объекта; инициализация очереди проверяется, а `sizeof(SsvcCommand)` в размере элемента не встречается.

**Тесты:** нативная сборка библиотеки + прицельный тест-обмен через очередь (если нативная инфраструктура позволяет FreeRTOS-шим); на ESP — лог обмена `CmdProcessor`/`TelemetryTask` без роста `Stack High Water Mark` в минус. До этого пункта нагрузочные испытания не запускать.

### Фаза 2 (F1/F2/F4). Клиентский жизненный цикл

**Места:** `interface/src/lib/api/ssvcApi.ts` (`startLogDownload`, `downloadLog`, `fetchLogStatus`, `cancelLogDownload`, `apiFetch`), `interface/src/routes/oc/logs/RectificationLogs.svelte` (`loadLogs`, `requestLog`, `cancelLog`, `logRequestId`, `logStatus`, `logError`).

**Шаги**
1. `startLogDownload` возвращает типизированный результат: `accepted` (202 + snapshot), `ready` (200 `text/csv` + Blob), `error` (HTTP status + backend `error`). Имена — внутренние для клиента.
2. `ready` → Blob сохраняется сразу, polling не запускается. `accepted` → последовательный polling с интервалом 500 мс, лимит 30 попыток удалить.
3. Timeout ожидания считать от последнего изменения состояния/роста `received`. Стартовые значения: idle timeout 15 с (backend 10 с), GET статуса ≤ 5 с, получение тела CSV ≤ 60 с.
4. Каждый fetch — с `AbortSignal` и таймаутом. HTTP-статус и backend `error` сохранять, не превращать в `null`/`false`. Общий `apiFetch` не менять глобально — только GET_LOG-путь.
5. Локальный UI-статус отделить от backend-снапшота: `starting / waiting / downloading / done / error / cancelled`. При timeout/ошибке явно завершить ожидание, ошибка показывается раньше устаревшего `receiving`.
6. После каждого `await` проверять поколение операции и отмену, включая момент после получения Blob и перед сохранением ссылки. Новое действие очищает старую ошибку; уход со страницы отменяет локальные запросы.
7. `URL.revokeObjectURL` вызывать не раньше фактического старта скачивания (отложенный revoke), чтобы не терять файл в браузере с отложенным кликом.

**Критерий (из ревью):** стартовый `200` сохраняется один раз; передача длиннее 30 опросов доходит до скачивания; зависший HTTP ограничен таймаутом; ошибка видна, а старая операция не сохраняет Blob.

**Тесты:** расширить `interface/tests/unit/api/ssvcApi.logs.test.ts` (200/202, error-ветки, отмена, отсутствие лимита 30); UI-сценарий «долгая передача» в существующей инфраструктуре тестов.

### Фаза 3 (P1/P2). Семантика ответа: ложный успех, matching, владение payload

**Места:** `SsvcCommandsQueue.cpp` (`commandProcessorTask`, `registerCallbackCommands`), `SsvcCommandsQueue.h` (`commandToExpectedBit`, `TIMEOUT`, `pushCommandInQueue`), `SsvcConnector.cpp` (`_telemetry`, `getLastMessage`, `getLastResponse`).

**Шаги**
1. В `commandProcessorTask` сбрасывать `command_success = false` непосредственно перед `xEventGroupWaitBits`: сейчас после успешного TX он остаётся `true`, и истёкший таймаут выглядит как успех.
2. Успех определять только по callback ожидаемого бита; ветка «бит не пришёл» не должна приводить к подтверждению.
3. Ввести точный matching: ответ сопоставлять с активным запросом (`request` + схема ответа), а не с подстрокой `"OK"`. Для `STATUS` задать ожидаемый бит/условие явно (сейчас в `commandToExpectedBit` его нет).
4. BIT9/BIT10/BIT11 оставить только как «будильник»; результат и payload хранить отдельно, привязанными к активной команде.
5. Убрать общий `lastMessage`/`lastResponse` как транспорт ответов: callback должен получать владеемый снимок кадра (копия под lock), а не читать общий `std::string` без синхронизации. `getLastMessage()`/`getLastResponse()` — под тем же lock.
6. Таймаут/потеря ответа классифицировать как «исход неизвестен» (`OutcomeUnknown`), а не успех; не переиспользовать прежний успешный payload для новой команды.
7. Исправить двойное преобразование времени: `TIMEOUT` уже задан в тиках, а `pushCommandInQueue` вновь применяет `pdMS_TO_TICKS`. Передавать миллисекунды и конвертировать один раз (или убрать повторную конверсию).
8. Ввести явную политику повторов: для неидемпотентных команд (NEXT/START/RESUME) слепой повтор после неоднозначной отправки запрещён.

**Критерий:** нет пути «timeout → success»; ответ AT не подтверждает NEXT; ответ другой команды/старый бит не подтверждает новую; payload команды не затирается телеметрией; при tick ≠ 1 мс длительность ожидания соответствует заданной.

### Фаза 4 (B2/B1/B3). Согласованная сессия: резервирование, синхронизация, deadlines

**Места:** `SsvcLogProtocol.h` (`Transfer`, `Status`), `SsvcCommandsQueue.cpp` (`commandProcessorTask`), `HandlerRegistrator.cpp` (`/rest/logs`, `/rest/logs/*`).

**Шаги**
1. Один mutex сессии на `Transfer` (промежуточный вариант — вместо широкого архитектурного рефакторинга). Защитить все чтения, переходы и контейнеры; HTTP получает snapshot по значению, не ссылки.
2. Расширить `Status`: `IDLE`, `QUEUED_LIST`, `WAITING_LIST`, `LIST_RECEIVED`, `QUEUED_FILE`, `WAITING_START`, `RECEIVING`, `COMPLETED`, `ERROR`, `DRAINING`. JSON-схему менять согласованно с Client/UI.
3. Резервирование до enqueue: атомарно записать `generation`, вид запроса и process id; повторный запрос того же файла возвращает текущий статус без новой команды, другого файла — `409`.
4. `beginFile`/`reset` в очереди не вызывать безусловно для уже зарезервированного запроса; переход в `WAITING_*` выполнять до записи в UART и учитывать отказ записи.
5. `enqueue=false` → `503` с `queue_full`, резерв снимается; отдельные deadline для очереди и ожиданий LIST/START (стартовое 10 с каждое), проверяемые независимо от HTTP-polling.
6. Не держать mutex во время UART/HTTP/FS-ожиданий, callback и enqueue: короткая критическая секция → отпустить → команда → при отказе откатить тот же generation.
7. Queue перед отправкой проверяет generation и допустимое состояние.
8. После отправки GET_LOG обычные команды не отправлять до завершения или окончания `DRAINING`; ожидание не блокирующим циклом, а отложенной отправкой в воркере. Аварийные команды не блокировать молча (см. Фазу 8).

**Критерий:** два клиента создают одну команду; `enqueue=false` не оставляет busy; потерянные LIST/START заканчиваются ошибкой; snapshot/reset/consume не гоняются; обычные запросы не вклиниваются в файл.

### Фаза 5 (T1–T4, P1/P2). RX: маршрутизация, framer, overflow, таймауты

**Места:** `SsvcConnector.cpp` (`_telemetry`), `SsvcLogProtocol.h` (`Transfer::consume`, `checkTimeout`), `SsvcConnector.h` (`SSVC_OPEN_CONNECT_BUF_SIZE`, `kRxRingBytes`, `kQueueSize`).

**Шаги**
1. Классифицировать кадр сразу после разбора JSON: GET_LOG/LIST/START/file → в `Transfer`; только обычная телеметрия → общий mailbox. Файловые кадры не должны ждать telemetry mutex, MQTT-публикации и подробного лога payload.
2. Не запускать GET_SETTINGS/VERSION при восстановлении связи, если GET_LOG зарезервирован/активен/дренируется — отложить до освобождения транзакции.
3. Не использовать `logTransferActive`, вычисленный до блокирующего чтения: брать актуальный статус после обработки кадра. При backlog продолжать чтение без фиксированной покадровой паузы (убрать 500 мс на кадр при потоке), короткие ограниченные проходы с уступкой планировщику вместо busy spin.
4. Убрать `uart_flush()` по `data_len > 4096`: это не проверка overflow ring 8192. Подключить `kQueueSize > 0` и обработку реальных событий (`UART_FIFO_OVF`, `UART_BUFFER_FULL`, framing/parity). Overflow инвалидирует активную сессию и ведёт к восстановлению, а не к успешному завершению.
5. Держать line accumulator между чтениями: читать блоками, компилировать строку до `\n` (учитывать `\r\n`), парсить только полную строку; `1024` оставить, последний байт под NUL.
6. Отдельные deadline: кадра — от первого байта, не продлевается новыми байтами (стартовое 5 с); сессии RECEIVING — 10 с без валидного прогресса, посторонние/повреждённые байты его не продлевают. Проверять deadline внутри ожидания, а не только снаружи чтения.
7. Oversize → дренировать до следующего `\n`, хвост не парсить отдельно. На invalid JSON ожидаемого файлового кадра — явная ошибка и перезапуск приёма; вне файловой сессии произвольный плохой JSON не превращать в GET_LOG-error.
8. Результат `consume()` учитывать вместе с состоянием: `false` может означать посторонний кадр. Сохранить проверки порядка чанков и завершение по `received == total`.

**Критерий:** файл принимается при занятом telemetry mutex; backlog не выбрасывается; START не вызывает старую паузу 500 мс; oversize/нет `\n`/битый финальный JSON дают ограниченное восстановление и конкретный error code.

### Фаза 6 (B4/F3). Отмена и обновление списка

**Места:** `HandlerRegistrator.cpp` (`HTTP_DELETE /rest/logs`, `/rest/logs` GET), `SsvcLogProtocol.h`, `SsvcCommandsQueue.cpp`, `ssvcApi.ts` (`cancelLogDownload`), `RectificationLogs.svelte` (`cancelLog`, `loadLogs`).

**Шаги**
1. Пометить queue-команды generation; DELETE инвалидирует generation; воркер пропускает отменённую команду до отправки. Если отправка уже началась — считать запрос отправленным и перейти в `DRAINING`.
2. До отправки отмена освобождает резерв; после отправки — `DRAINING` вместо `reset()` в `IDLE`. Поздний START не принимать как новый запрос; блокировать новый GET_LOG/LIST до восстановления границы старого потока.
3. В `DRAINING` читать и отбрасывать только кадры старой передачи; признак завершения — известный финальный чанк, возобновившаяся телеметрия или проверенное условие. Одна пауза тишины не доказывает конец передачи: при отсутствии надёжного признака оставлять `RecoveryRequired`, а не «готов».
4. REST: `statusOnly=1` (только snapshot) и `refresh=1` (явный запрос списка) — новые необязательные параметры, текущий GET без параметров остаётся совместимым. `refresh` в активной файловой сессии → `409` без reset; повторный refresh при активном списке возвращает его статус.
5. UI: при отмене сначала инвалидировать локальное поколение и прервать запросы, затем учитывать ответ DELETE; отказ отмены показывать явно; не вызывать GET, который сам запускает LIST, сразу после отмены.
6. `loadLogs()` очищает прежнюю ошибку; ошибку контроллера не маскировать под пустой список.

**Критерий:** отменённая queued-команда не отправляется; поздний START не возрождает операцию; старая HTTP-операция не сохраняет Blob; первый клик показывает поздно пришедший список, повторный действительно его обновляет; ERROR не блокирует восстановление.

### Фаза 7 (B5/H1). Base64 и время жизни результата

**Места:** `SsvcLogProtocol.h` (`detail::decodeBase64`, `Transfer::data`, `LOG_TOTAL_RAW_MAX`), `HandlerRegistrator.cpp` (ветка `COMPLETED`).

**Шаги**
1. Заменить signed accumulator на ограниченный unsigned или декодирование группами по 4 символа; валидировать алфавит, позицию/количество padding и длину; повреждённый чанк не принимать как успешный.
2. Сохранить побайтовый CSV, лимит итогового размера и проверку последовательности чанков; UART-контракт и CRC не менять.
3. Убрать `reset()` результата до доставки CSV: повторный GET того же completed process id отдаёт те же байты без новой UART-команды; ресурс удерживается до завершения/обрыва отправки и освобождается после последнего читателя.
4. Не возвращать ссылки на mutable `std::string` после освобождения lock и не дублировать весь CSV в нескольких строках; metadata snapshot отделить от ресурса результата.
5. Снять измерения heap/free largest block перед выбором схемы хранения. Если RAM недостаточно — временное хранилище с bounded-буферами и потоковой выдачей, проверка каждой записи и общего лимита; отказ → `storage_error`, не `COMPLETED`.
6. Не объявлять OOM/H1 доказанной причиной: до замеров решение по памяти помечать как неподтверждённое.

**Критерий:** 600 разнообразных байт восстанавливаются точно; padding для остатков 1/2 байта корректен; плохая Base64 → `invalid_data`; обрыв HTTP не уничтожает completed; повтор отдаёт идентичные байты; пиковая память не растёт из-за дублирования полного файла.

### Фаза 8 (P2/P1). Запуск, готовность и аварийные команды

**Места:** `SsvcConnector.cpp` (`SsvcConnector()`, `InitUartDriver`, `initSsvcController`), `SsvcCommandsQueue.cpp` (`SsvcCommandsQueue()`, `commandProcessorTask`, `sendAT`, `scheduleUartRetryTimer`), `SsvcCommandsQueue.h` (`COMMAND_MAP`), `CommandHandler.cpp` (`handleCommand`).

**Шаги**
1. Убрать `InitUartDriver()` из конструктора и запуск задач до готовности зависимостей: явная однократная инициализация (синхронизация/очереди → драйвер → задачи → handshake → `Ready`).
2. Проверять результат `xTaskCreatePinnedToCore` (сейчас `nullptr`-handle без проверки, приоритет `tskIDLE_PRIORITY`); при отказе — `Failed/NotReady` и корректный cleanup.
3. Не запускать воркер при `command_queue == nullptr`; заменить стартовую паузу 6 с (`vTaskDelay` в начале `commandProcessorTask`) на явную готовность/handshake.
4. Хранить `Ready/Failed`, `LinkState` и причину отказа раздельно; никаких UART-команд через частично созданный singleton.
5. `emergency_stop`: вывести из общего FIFO — отдельный admission для допустимых stop/safety запросов, приоритет перед неотправленными обычными командами; queued START/NEXT/RESUME, ставшие опасно устаревшими, инвалидировать по политике.
6. Уже отправленную команду не «отменять» удалением локального дескриптора: при preemption результат становится неизвестным, старый ответ не подтверждает новую safety-команду.
7. Пробросить результат постановки в REST: `CommandHandler::handleCommand` сейчас отвечает `200 Command accepted` независимо от `enqueue=false`. Для void-обёрток (`stop`, `next`, …) возвращать результат `pushCommandInQueue` и отдавать `503`/`409` с причиной (`lastRejectionReason`/`lastRejectedFeature`).
8. Не блокировать safety новой политикой файла: при прерывании GET_LOG — дренирование, но STOP не ждёт файл.

**Критерий:** нет старта задач из конструктора и до готовности драйвера; отказ init/queue-create виден как `NotReady`; REST не отвечает `accepted` при отказе постановки; STOP не зависит от заполненного обычного FIFO.

### Фаза 9. Проверки и приёмка

**Существующая инфраструктура:** `test/native/test_ssvc_log_protocol/test_main.cpp` (парсер), `interface/tests/unit/api/ssvcApi.logs.test.ts` (клиент). Новую инфраструктуру не ставить; UI-сценарии добавить в существующую.

**Целевые проверки по фазам**

| Проверка | Фаза |
|---|---|
| Обмен через очередь без выхода за границы объекта | 1 |
| Стартовые 200/202, обрыв HTTP, повтор GET, отсутствие лимита 30 опросов | 2 |
| Timeout ≠ success; AT не подтверждает NEXT; late reply не подтверждает новую команду | 3 |
| Два клиента/двойной клик → одна команда; `enqueue=false` → `503` без busy | 4 |
| Занятый telemetry mutex, backlog, отсутствие `\n`, oversize, битый финальный JSON | 5 |
| Cancelled generation, поздний START, drain, refresh/statusOnly, ERROR → повтор | 6 |
| 1 / 599 / 600 / 601 байт, длинные ненулевые Base64, padding, размер около лимита | 7 |
| Init/task-create failure → NotReady; REST при отказе постановки; STOP при полном FIFO | 8 |

**Критерий:** сравниваются байты CSV, а не только boolean/HTTP-статус; непроверенные аппаратные условия выписаны отдельно; формулировки «исправлено на устройстве»/«тесты прошли» не используются без фактического запуска.

### Порядок и зависимости

1. Фаза 0 — всегда первая.
2. Фаза 1 (P0) — жёсткий блокер, до любых нагрузочных испытаний.
3. Фазы 2 и 3 независимы друг от друга (frontend и C++-семантика) и могут идти параллельно.
4. Фаза 4 — фундамент для 5–7: состояния, mutex, generation.
5. Далее 5 (RX) → 6 (отмена/список) → 7 (Base64/хранение).
6. Фаза 8 — запуск/готовность/аварийные команды; выполняется после 4, чтобы не менять модель владения дважды.
7. Фаза 9 — приёмка каждой фазы плюс сквозные сценарии в конце.

### Риски

| Риск | Митигация |
|---|---|
| Смена модели владения дважды (mutex сессии → SessionTask) | в этом плане целевое состояние — одна модель с mutex/generation; переход к отдельному SessionTask — только отдельным решением |
| Правки `Status`/JSON ломают совместимость с UI и внешними клиентами | новые состояния и параметры (`statusOnly`, `refresh`) вводить аддитивно, старый GET без параметров оставить совместимым |
| Ужесточение таймаутов/повторов ухудшает работу при медленном контроллере | значения 5/10/15/60 с — стартовые, подтверждать замером; не менять UART-контракт |
| Поведение контроллера при командах во время GET_LOG неизвестно | проверка по протоколу и стенду; при неизвестности — `RecoveryRequired`, а не «безопасно» |
| Нет доказательства, что H1/OOM — причина жалобы | измерения heap до выбора схемы хранения; решение по памяти — явно помечать как неподтверждённое |
| Файлы-образцы ревью могут разойтись с кодом после правок | номера строк в источниках — ориентиры; поиск по символам, не по строкам |
