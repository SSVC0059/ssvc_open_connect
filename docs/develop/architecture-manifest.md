# Манифест архитектуры: IoT-проект на базе ESP32SvelteKit

> **Что это.** Навигационная карта архитектуры для LLM-агента, работающего над проектом на базе фреймворка ESP32SvelteKit (ESP32 + встроенный SvelteKit-фронтенд). Документ описывает **паттерны и места их применения**, а не бизнес-логику конкретного продукта.
>
> **Как пользоваться.** Это указатель «где искать», а не источник истины. Перед изменениями всегда проверяй фактический код: он приоритетнее текста. Если паттерн в проекте отсутствует — бери его из референс-реализации (см. §11).
>
> **Правило трёх шагов для любой задачи:**
> 1. Определи слой (§3) — куда относится изменение.
> 2. Найди в репозитории уже существующий аналог (§8) — новый код должен повторять его структуру.
> 3. Воспроизведи паттерн (§4–§6), не изобретая новый.

## 1. Что это за система

Единая прошивка, в которую упакованы три подсистемы:

| Часть | Технология | Где живёт |
|---|---|---|
| Прошивка | PlatformIO, Arduino-фреймворк, ESP32 (FreeRTOS) | `src/`, `lib/` |
| Логика приложения (C++) | C++17, ArduinoJson, ESPAsyncWebServer, LittleFS, PsychicMqttClient | `lib/<app>/` |
| Веб-интерфейс | Svelte 5 + SvelteKit 2 (SPA, adapter-static), Tailwind CSS 4 + DaisyUI 5 | `interface/src/` |
| Файловая система | LittleFS (`ESPFS`) — конфиги + статика | `data/`, раздел FS в `boards/*.csv` |

Каналы взаимодействия фронтенда с устройством:

- **REST** (`/rest/...`) — основные данные и настройки;
- **WebSocket** (`/ws/events`) — push-события (MessagePack по умолчанию, JSON через `EVENT_USE_JSON`);
- **MQTT** — интеграция с внешними системами, топики `<namespace>/...`.

Прошивка работает по модели «arduino-скетч + задачи FreeRTOS»: `setup()` инициализирует всё, `loop()` может быть пустым (работа вынесена в задачи). Главный принцип — **всё состояние проходит через сервисы состояния (`StatefulService`)**, а HTTP/MQTT/WebSocket — лишь адаптеры над ними.

## 3. Слои и правила зависимостей

Направление зависимостей — строго «вниз», без циклов:

```
src/main.cpp
   └── API (HTTP-хендлеры)         ──► core, components, framework
   └── core (оркестрация, сервисы) ──► components, external, framework
   └── components (драйверы)       ──► commons, framework
   └── commons (утилиты)           ──► framework
lib/framework  ◄── используется всеми, сам никого не знает (вендорский код)
```

Инварианты:

- `lib/framework/` — **read-only**. Нужное поведение наращивается снаружи (наследование, композиция, подписки на хуки сервисов).
- Доменную логику не кладут в `components/` — там только «железо» и его обвязка.
- `components/` и `commons/` не знают о HTTP.
- API-слой не хранит состояние: только читает/пишет через сервисы.

## 4. Паттерны фреймворка (ядро)

### 4.1 Сервис состояния + эндпоинты + персистентность

Центральный паттерн проекта. Состояние живёт в `StatefulService<T>`; HTTP, MQTT и WebSocket — подключаемые адаптеры; сохранение в LittleFS — ещё один подписчик.

Роли в одном сервисе:

| Класс | Роль |
|---|---|
| `T` (структура данных) | сами поля + функции `read(const T&, JsonObject&)` и `update(JsonObject&, T&, originId)` |
| `StatefulService<T>` | потокобезопасное состояние: `update`/`read`, `addUpdateHandler`, `addHookHandler` |
| `HttpEndpoint<T>` | GET/POST по пути `/rest/...` |
| `MqttEndpoint<T>` | publish/subscribe топиков (с троттлингом через `MqttCommitHandler`) |
| `EventEndpoint<T>` | WebSocket-событие с автосинхронизацией на фронт |
| `FSPersistence<T>` | автосохранение JSON в LittleFS на каждый `CHANGED` |

Скелет нового сервиса:

```cpp
// XxxState.h
struct XxxState {
  uint32_t intervalMs = 1000;
  bool enabled = true;

  static void read(const XxxState &state, JsonObject &root) {
    root["interval_ms"] = state.intervalMs;
    root["enabled"] = state.enabled;
  }
  static StateUpdateResult update(JsonObject &root, XxxState &state, const String &originId) {
    XxxState next = state;
    if (root["interval_ms"].is<uint32_t>()) next.intervalMs = root["interval_ms"];
    if (root["enabled"].is<bool>())        next.enabled = root["enabled"];
    if (next.intervalMs == state.intervalMs && next.enabled == state.enabled)
      return StateUpdateResult::UNCHANGED;
    state = next;
    return StateUpdateResult::CHANGED;   // CHANGED → сработают подписчики
  }
};

// XxxService.h
class XxxService : public StatefulService<XxxState> {
public:
  XxxService(AsyncWebServer *server, FS *fs, SecurityManager *sm)
    : _httpEndpoint(XxxState::read, XxxState::update, this, server, "/rest/xxx", sm),
      _fsPersistence(XxxState::read, XxxState::update, this, fs, "/config/xxx.json") {}

  void begin() {
    _fsPersistence.readFromFS();   // дефолты → файл, если файла/парсинга нет
    _httpEndpoint.begin();
  }
private:
  HttpEndpoint<XxxState> _httpEndpoint;
  FSPersistence<XxxState> _fsPersistence;
};
```

Правила:

- Возвращать `CHANGED` **только** при реальном изменении — иначе получится лавина публикаций.
- `updateWithoutPropagation` — для загрузки/миграции; `update` — для рантайма.
- Путь в FS: `/config/<domain>.json`; промежуточные каталоги создаются автоматически.
- Подписка на изменения: `addUpdateHandler([](const String &originId){ ... }, allowRemove)`.

### 4.2 Безопасность API

Все маршруты регистрируются через `SecurityManager`:

```cpp
_server.on(path, HTTP_GET,
           _securityManager->wrapRequest(handler, AuthenticationPredicates::IS_AUTHENTICATED));
_server.addHandler(new AsyncCallbackJsonWebHandler(path,
           _securityManager->wrapCallback(callback, AuthenticationPredicates::IS_AUTHENTICATED)));
```

- Предикаты: `IS_AUTHENTICATED`, `IS_ADMIN` (см. `SecurityManager.h`).
- Пароль/JWT-логика — целиком в `SecuritySettingsService` / `AuthenticationService`, дублировать её в прикладном коде нельзя.
- **Порядок регистрации маршрутов:** длинные пути раньше коротких (`/rest/profiles/content` до `/rest/profiles`) — иначе перехватит короткий матчер.
- Формат ответа: JSON через `AsyncJsonResponse`; ошибки — короткий JSON `{"error":"..."}` с корректным кодом (400/404/409/500).

### 4.3 Фичи: компиляция + рантайм

Два независимых механизма, не путать:

| Механизм | Область | Как использовать |
|---|---|---|
| `FT_*` макросы (`Features.h`) | Сборка: код и поля класса исключаются препроцессором | `#if FT_ENABLED(FT_MQTT) ... #endif`; флаги задаются в `platformio.ini`/`features.ini` |
| `FeaturesService` | Рантайм: JSON `GET /rest/features` + событие `features` | `featureService->addFeature("myFeature", true)` для динамических возможностей |

`FT_ENABLED(x)` — просто `x`; значение по умолчанию задаётся `#ifndef` в `Features.h`. Фронтенд получает флаги из `GET /rest/features` в корневом layout и **обязан** скрывать/отключать соответствующую функциональность.

### 4.4 События в браузер

`EventSocket` — транспорт (`/ws/events`, MessagePack/JSON, аутентификация по `access_token`).
`EventEndpoint<T>` — готовый адаптер для состояния: при `CHANGED` эмитит событие, при подписке клиента отправляет текущее значение.

```cpp
EventEndpoint<XxxState> _eventEndpoint;  // конструктор: reader, updater, this, socket, "xxx"
void begin() { _eventEndpoint.begin(); }
```

Правило: для «состояние изменилось → уведомить UI» использовать `EventEndpoint`, а не ручной `emitEvent`; имя события = имя домена в camelCase.

### 4.5 MQTT

- Клиент — из `MqttSettingsService` (`getMqttClient()`); собственную MQTT-сессию не поднимать.
- Публикация состояния — `MqttEndpoint<T>` (QoS/retain задаются в конструкторе); троттлинг публикаций — статический таймер `MqttCommitHandler` (`setTimerInterval`).
- Именование топиков: `<namespace>/<domain>[/<sub>][/state|/set|/pub]`; команды — отдельный топик, ответы — парный ему.
- Внешние интеграции, требующие сложной подписки/переподписки, оборачивать в собственный bridge-слой (§5.6).

### 4.6 Файловая система и веб-статика

- Всегда работать через `ESPFS` (`lib/framework/ESPFS.h` → `LittleFS`), не через `LittleFS.h` напрямую.
- Конфиги — обычные JSON-файлы через `FSPersistence`; для «не-состояний» (метаданные, списки) — прямое чтение/запись JSON на `ESPFS`.
- Веб-статика попадает в прошивку двумя способами: `EMBED_WWW` (gzip в PROGMEM, генерируется на сборке) либо заливка в LittleFS (`data/www`, target `uploadfs`). Имена ассетов ограничены длиной, поэтому сборка чистит хеши в именах.
- Каталог `/config/` — конфиги; каталог статики монтируется отдельно. Перед работой с FS проверять `ESPFS.begin()` (вызывается фреймворком в `ESP32SvelteKit::begin()`).

### 4.7 Жизненный цикл и задачи

```cpp
void setup() {
  AsyncWebServer server(80);
  ESP32SvelteKit kit(&server);
  kit.begin();                       // фичи, FS, WiFi/AP, сервисы фреймворка
  App::getInstance().begin(server, kit, kit.getSocket(), kit.getSecurityManager());
}
void loop() { vTaskDelete(nullptr); }  // вся работа — в задачах
```

- Длительная работа — только отдельные FreeRTOS-задачи/таймеры (`xTaskCreate`, `xTimerCreate`); периодический код в `loop()` не кладём.
- Для «своего» периодического кода без потока есть `ESP32SvelteKit::addLoopFunction(cb)`.
- Порядок инициализации критичен: сервисы состояния → подписки на профили/конфиги → подсистемы (`begin()` подсистем) → хендлеры HTTP → интеграции, требующие сети.
- Блокирующее ожидание сети — только на последнем шаге инициализации, с логом и таймаутом.

## 5. Паттерны приложения (core / components)

### 5.1 Подсистемы (Subsystem)

Единый способ включать/выключать узел функциональности в рантайме, с сохранением состояния в NVS.

```cpp
class MySubsystem : public Subsystem {
public:
  static std::string getName() { return "my_subsystem"; }
  void initialize() override;   // разовая настройка
  void enable() override;       // старт (задача/таймер)
  void disable() override;      // корректная остановка
};
// регистрация:  SubsystemManager::instance().registerSubsystem<MySubsystem>();
//               SubsystemManager::instance().registerSingleton<I2CBusSubsystem>();
```

- `initialize()` вызывается для всех зарегистрированных подсистем, `enable()` — вторым проходом и только для включённых.
- Состояние включённости хранится в NVS (`setInitialState` — дефолт для новой подсистемы).
- Подсистема не должна сама себя регистрировать — только через точку сборки приложения (§4.7).

### 5.2 Сенсоры и опрос

Два интерфейса, разделять их:

| Интерфейс | Ответственность |
|---|---|
| `AbstractSensor` | одно устройство: `readValue()`, `getData()`, `getUnit()`, `getType()`, `getMeasurementType()`, валидность данных |
| `PollingSubsystem` | источник данных: `initialize()`, `poll()`, `getName()` |

Поток данных: `SensorCoordinator` (планировщик по таймеру) → `poll()` всех `PollingSubsystem` → `SensorManager` (реестр сенсоров) → сервис данных (`StatefulService`) → HTTP/MQTT/UI.

Правило добавления датчика: новый класс `AbstractSensor` + подсистема-источник + регистрация в реестре + конфиг + эндпоинт + UI. Ни один шаг не пропускать — иначе датчик будет виден только половине системы.

### 5.3 Сервисы-состояния приложения

Все настраиваемые сущности оформляются как сервисы (§4.1). Типовой набор на домен:

- структура состояния + `read`/`update`;
- `HttpEndpoint` на `/rest/<domain>`;
- `FSPersistence` на `/config/<domain>.json`;
- при необходимости — `MqttEndpoint` и `EventEndpoint`;
- метод `begin()`, вызываемый из точки сборки приложения.

### 5.4 HTTP-слой приложения

Разделение обязанностей:

- **handler** — класс с набором функций-обработчиков, вызываемых лямбдами (`getInfo`, `updateSettings`, …); получает зависимости в конструкторе;
- **registrator** — только регистрация маршрутов (`registerXxxHandlers()`), без логики;
- **фасад** — владеет объектами хендлеров и регистратором, единственный публичный `begin()`.

Правила: логика — в handler'е (через сервисы), маршруты — в registrator; путь и метод описывают ресурс; доменные префиксы (`/rest/<domain>/...`).

### 5.5 Уведомления и алерты

Паттерн «источник события → набор независимых подписчиков»:

```cpp
class MySubscriber : public IAlarmSubscriber {
public:
  MySubscriber()  { AlarmMonitor::getInstance().subscribe(this); }
  ~MySubscriber() { AlarmMonitor::getInstance().unsubscribe(this); }
  void onAlarm(const AlarmEvent &event) override;
};
```

- Источник (`AlarmMonitor`) сам решает, когда событие возникло, и рассылает его подписчикам.
- Подписчик — самостоятельный модуль: логирование, push в UI (`NotificationService`), GPIO, внешний мессенджер. Один подписчик не должен знать о других.
- Состояние алерта держится в сервисе порогов, а не в подписчиках.

### 5.6 Системные примитивы и соглашения

| Тема | Правило |
|---|---|
| Синглтоны | Meyers (`static X& getInstance()`) для инфраструктуры; для сервисов, создаваемых в `begin()`, — создание в точке сборки + `setInstance()` |
| Персистентные настройки | NVS (`Preferences` через обёртку `GlobalConfig`) — для рантайм-флагов; JSON в LittleFS — для пользовательских конфигов |
| Большие JSON | PSRAM-аллокатор (`commons/`) для документов килобайтного масштаба |
| Синхронизация | `std::mutex` / FreeRTOS-семафоры; RAII-обёртка `MutexLocker` вместо ручных `take/give` |
| Обмен структурами между задачами | Снимок под мьютексом (`getSnapshot()`), а не прямая ссылка на живое состояние |
| Логи | `static constexpr auto TAG` в классе + `ESP_LOGI/W/D/E(TAG, ...)`; в лог — идентификатор источника |
| Ошибки драйверов | Возвращать `bool`/код + логировать; не «глотать» отказы I2C/UART |
| Внешние интеграции | Отдельный каталог `external/`, собственные worker-задачи, никаких блокирующих вызовов в общих задачах |

## 6. Frontend (SvelteKit SPA)

### 6.1 Стек и устройство

- Svelte 5 (runes: `$state`, `$derived`, `$effect`, `$props`) + SvelteKit 2, **adapter-static**, `ssr=false`, `fallback: index.html`.
- Tailwind CSS 4 + DaisyUI 5 подключаются через Vite-плагин; отдельного `tailwind.config` нет, токены темы — CSS-переменные в `src/app.css`.
- SCSS — только для легаси/исключений (миксины, анимации); новый код — на утилитах Tailwind/DaisyUI.
- Иконки — через `unplugin-icons` (`~icons/...`).
- Сборка: `scripts/pio/` (npm-сборка → `EMBED_WWW` или `data/www` + uploadfs).

### 6.2 Слои

| Слой | Путь | Правило |
|---|---|---|
| Роутинг/каркас | `src/routes/` | `+layout.svelte` — каркас (навигация, статус-бар, модалки, тосты, инициализация WS); `+layout.ts` — загрузка фич приложения; `+page.ts` — заголовок страницы |
| Страницы | `src/routes/<раздел>/` | тонкая обёртка над компонентом-контейнером; вкладки — через query-параметр |
| Компоненты | `src/lib/components/<Feature>/` | по папке на домен; переиспользуемые примитивы — в корне `components/` |
| API | `src/lib/api/` | единая обёртка `apiFetch<T>` → дискриминированный результат `{success,data}|{success,error}`; все вызовы только через неё |
| Состояние | `src/lib/stores/` | Svelte-сторы для глобального (пользователь, сокет, аналитика), runes — для локального |
| Типы | `src/lib/types/` | DTO синхронизируются с backend вручную; имя поля = имя JSON-ключа |
| Утилиты/экшены | `src/lib/utils/`, `src/lib/actions/` | форматтеры, валидаторы, Svelte actions |

### 6.3 Навигация, авторизация, фичи

- Пункты меню описываются массивом объектов с полями `title/icon/href/feature` и фильтруются по флагам из `GET /rest/features` (и по признаку администратора).
- Авторизация: токен в сторе пользователя; заголовок `Authorization: Bearer ...` (или Basic, если фича безопасности выключена). Проверка — при инициализации layout; при ошибке — экран логина.
- Функциональность, зависящая от версии прошивки/API, гейтится явно: компонент-баннер «не поддерживается» или action, блокирующий узел. Сравнение версий — числовым кодом `major*100+minor`, **не** строкой/float.

### 6.4 Realtime

- WebSocket-сокет — обёртка над браузерным `WebSocket` с реконнектом и ping-таймаутом; формат — MessagePack (или JSON), подписка на события — по имени.
- Обработка событий централизована в корневом layout: событие → обновление соответствующего стора → UI.
- Для «тяжёлых»/редко меняющихся данных допустим поллинг страницы; для мгновенных уведомлений — WS.

### 6.5 Стиль

- База: DaisyUI-компоненты и Tailwind-утилиты; тёмная тема — через `prefersdark` + переменные темы.
- Глобальные стили общих элементов (кнопки, поля, модалки, вкладки) задаются централизованно в layout/`app.css`, а не раскидываются по компонентам.
- Состояния обязательны: загрузка (`Spinner`), пустое состояние, ошибка, «нет прав/не поддерживается».

## 7. Конвенции и инварианты

### 7.1 Структура кода

- «Папка на класс»: `<ClassName>/<ClassName>.{h,cpp}`. Исключения — заголовочные компоненты из одной пары `initialize/enable/disable`.
- Сначала `.h` с интерфейсом и комментарием о назначении, затем `.cpp`. Заголовок не тянет тяжёлые зависимости без необходимости.
- Порядок членов класса: публичный API → приватные данные → приватные методы. Константы и `TAG` — рядом с использующим их кодом.
- Имена: классы — `PascalCase`, методы/поля — `camelCase`, приватные поля — с ведущим `_`, константы времени компиляции — `UPPER_SNAKE`, статические строки путей/топиков — `UPPER_SNAKE` константа в классе.

### 7.2 Жёсткие инварианты

| Инвариант | Почему |
|---|---|
| `lib/framework/` не редактируется | обновляемость фреймворка; кастомизация — снаружи |
| Состояние меняется только через `StatefulService::update` | иначе не сработают подписчики, MQTT, WS и сохранение в FS |
| Возврат `UNCHANGED` при отсутствии изменений | защита от шторма публикаций и записей в FS |
| Долгие пути маршрутов регистрируются раньше коротких | иначе маршрут перехватится матчером |
| Версии сравниваются числовым кодом | `“1.10” > “1.9”` строкой — неверно |
| Блокирующих вызовов нет в общих задачах и колбэках | голодание задач, срабатывание watchdog |
| Новый код не тянет доменные сущности из примера | переносится паттерн, а не предметная область |
| Фича без флага `FT_*`/`addFeature` не «прячется» | фронт должен знать, что поддерживается, а что нет |

### 7.3 Память и производительность

- Бюджеты: PSRAM — для крупных JSON и буферов; DRAM — под задачи и стеки. Стек задачи задавать с запасом, следить за `getMinFreeHeap()`.
- Строки: избегать конкатенации в цикле, использовать `reserve`, при необходимости — string-view.
- JSON: парсить в документ нужного размера, не держать одновременно несколько крупных документов.
- Тяжёлый RT-код (тайминги, опрос) не мешать с сетевой обработкой — разные задачи/приоритеты.

### 7.4 Документация и изменения

- Ведётся `CHANGELOG.md` (Keep a Changelog + SemVer, разделы «Новое/Исправлено/Улучшения/Документация»).
- Новый REST-эндпоинт отражается в `docs/develop/api/`; новый протокольный обмен — в соответствующем разделе `docs/`.
- Версию приложения задаёт `APP_VERSION` (макрос сборки), версию внешнего протокола — отдельные константы целевой/минимальной версии.

## 8. Карта «задача → где менять»

| Задача | Точки входа (в порядке правок) |
|---|---|
| Новая настройка, сохраняемая на устройстве | структура состояния + `read`/`update` → `StatefulService` → `HttpEndpoint` → `FSPersistence` → `begin()` в точке сборки → UI: тип + функция API + форма |
| Новый REST-эндпоинт (действие, не состояние) | handler в `API/handlers/<Domain>/` → регистрация в `HandlerRegistrator` → фронт: `api/<Domain>.ts` |
| Новый сенсор/источник данных | `AbstractSensor` → `PollingSubsystem` → регистрация в реестре сенсоров → подсистема → конфиг + миграция → эндпоинт → UI-секция |
| Новая подсистема (устройство/узел) | класс `Subsystem` + `getName()` → `registerSubsystem`/`registerSingleton` в точке сборки → конфиг включённости |
| Новая интеграция с внешним сервисом | `external/<Vendor>/` (клиент + своя задача) → сервис настроек → подсистема → handler настроек → UI-вкладка |
| Новое уведомление/алерт | состояние порогов в сервисе → источник события → `IAlarmSubscriber`-подписчик → канал доставки (UI push / внешний мессенджер) |
| Новый MQTT-топик | `MqttEndpoint<T>` на существующем сервисе состояния либо bridge-слой для сложной логики |
| Новая страница/вкладка UI | `routes/<раздел>/+page.svelte` (+ `+page.ts`) → компонент-контейнер в `lib/components/<Feature>/` → пункт меню с `feature`-гейтом → тип + API-функция |
| Новый флаг функциональности | `Features.h` (`FT_*`, если код можно исключить сборкой) или `addFeature()` (если фича динамическая) → гейт в UI |
| Изменение протокола внешнего устройства | спецификация версии/валидаторы → очередь команд → сервис состояния-разбора → гейт по версии на фронте |

## 9. Антипаттерны

- Править `lib/framework/`, чтобы «добавить фичу» — вместо этого композиция/подписка из приложения.
- Хранить состояние в статических переменных/глобальных объектах в обход `StatefulService`.
- Регистрировать HTTP-маршруты прямо в прикладном коде, минуя общий registrator (маршруты перестают быть обозримыми).
- Публиковать в MQTT/WS из середины логики, а не из подписчика на изменение состояния.
- Делать `poll()`/сетевой вызов внутри обработчика HTTP-запроса.
- Возвращать `CHANGED` «на всякий случай» — вызывает каскад записей в FS и публикаций.
- Копировать в новый проект предметные сущности примера (названия домена, поля протокола, экраны) вместе с паттерном.
- Тянуть `Arduino.h`/HTTP-типы в заголовки, где достаточно вперёд-объявления (рост времени сборки и связности).
- Хардкодить топики/пути строкой в нескольких местах вместо одной константы.

## 10. Рабочий процесс LLM-агента

**Перед изменениями:**

1. Классифицировать задачу по §8 — это определяет список затрагиваемых файлов.
2. Найти существующий аналог в референс-реализации (§11) через поиск по имени паттерна (`StatefulService`, `HttpEndpoint`, `Subsystem`, `PollingSubsystem`, `IAlarmSubscriber`, `HandlerRegistrator`, `apiFetch`, `stores/`).
3. Прочитать аналог целиком (и `.h`, и `.cpp`/`.svelte`) — новый код должен быть неотличим по стилю.

**Во время изменений:**

- Одно изменение — один слой: не смешивать правку драйвера, сервиса и UI в одном шаге.
- Сохранять симметрию: если добавлено поле состояния — добавить его и в `read`, и в `update`, и в тип на фронте, и в UI.
- Не удалять и не переименовывать существующие константы путей/топиков без необходимости — на них завязаны фронт и внешние системы.
- Не коммитить сгенерированные артефакты сборки.

**Проверка перед завершением:**

| Что | Как |
|---|---|
| Прошивка собирается | `pio run` (нужный env) |
| Юнит-тесты | `pio test -e native`, `npm run test:run` в `interface/` |
| E2E (если затронут UI-флоу) | Playwright-набор в `e2e/` |
| Фича-флаги | новая фича скрыта при выключенном `FT_*`, UI это учитывает |
| Безопасность | новые маршруты зарегистрированы через `SecurityManager` с корректным предикатом |
| Версия API | если добавлена возможность протокола — обновлён гейт версии на фронте |
| Документация | запись в `CHANGELOG.md`; при новом API — раздел `docs/develop/api/` |

**Если аналога нет** — не изобретать новую архитектуру в одиночку: реализовать минимальным расширением существующих паттернов (§4–§6) и явно сообщить пользователю о принятом решении.

## 12. Глоссарий

| Термин | Значение |
|---|---|
| **Сервис состояния** (stateful service) | Класс, владеющий данными приложения и уведомляющий подписчиков об изменениях; основа всей архитектуры |
| **Эндпоинт** | Адаптер сервиса состояния к внешнему интерфейсу (HTTP / MQTT / WebSocket) |
| **Персистентность** | Автосохранение состояния сервиса в JSON-файл на LittleFS |
| **Подсистема** | Включаемый в рантайме узел функциональности с сохранением состояния (обычно вокруг устройства или внешней службы) |
| **PollingSubsystem** | Источник данных, опрашиваемый планировщиком по таймеру |
| **Хендлер** | Обработчик HTTP-запроса домена; **регистратор** — централизованная регистрация маршрутов |
| **Фича-флаг** | Признак доступности функциональности: компиляционный (`FT_*`) или рантайм (`/rest/features`) |
| **Origin ID** | Идентификатор источника изменения состояния (`http`, `mqtt`, `ws`, `fs`) — используется для фильтрации и отладки |
| **Профиль** | Именованный набор пользовательских настроек, применяемый к сервисам состояния |
| **Манифест** | Настоящий документ: карта архитектуры и паттернов для LLM-агента |
