# План поддержки UART API v1.10

## Область анализа

Документ подготовлен по результатам сравнения:

- текущей ветки `main` репозитория `ssvc-open-connect`;
- публичной спецификации UART API v1.9;
- предоставленной спецификации UART API v1.10.

В версии v1.10 основное новое функциональное изменение — удалённое скачивание
логов процессов через команду `GET_LOG`. Дополнительно в telemetry этапа
`hearts` появилось поле `preempt_cnt`.

Параметры `formula=0|1|2`, `predec`, `extended_heads`, а также поля `cfg_chgd`
и `tts` уже описаны в доступной спецификации v1.9. Они включены в план как
задачи полной совместимости текущей реализации со спецификацией, но не
считаются изменениями v1.9 → v1.10.

## Изменения v1.9 → v1.10

### Команда `GET_LOG`

Команда работает только в дежурном режиме контроллера:

```text
GET_LOG
GET_LOG <номер_процесса>
```

Без номера процесса контроллер возвращает список CSV-файлов:

```json
{
  "type": "response",
  "request": "GET_LOG",
  "result": "LIST",
  "files": ["15.CSV", "16.CSV", "17.CSV"]
}
```

При указании номера процесса начинается пакетная передача файла. Сначала
приходит мета-пакет:

```json
{
  "type": "response",
  "request": "GET_LOG",
  "result": "START",
  "file": "15.CSV",
  "total": 335
}
```

Затем передаются пакеты:

```json
{
  "type": "file",
  "chunk": 1,
  "data": "<base64>"
}
```

`data` содержит Base64-кодированный чанк до 600 байт исходных данных.
Передача завершается после получения чанка с номером `total`. На время
операции регулярная telemetry приостанавливается.

Возможные ошибки:

- `err_num` — неверный номер процесса;
- `err_mnt` — ошибка монтирования файловой системы;
- `err_nf` — файл не найден или недоступна директория логов;
- `err_int` — внутренняя ошибка передачи.

### Новое поле telemetry

Для сообщения `type: "hearts"` добавляется:

- `preempt_cnt` — количество упреждающих снижений скорости отбора.

## План backend

### 1. Модель протокола UART

- Добавить `GET_LOG` в список команд и карту команд.
- Поддержать формирование запросов без номера и с числовым номером процесса.
- Добавить отдельные модели или структуры для ответов `LIST`, `START`, `file` и
  ошибок.
- Разделить обработку обычных response-пакетов и `type: "file"`.
- Реализовать состояние передачи:
  `idle → started → receiving → completed/error`.
- Проверять `total`, последовательность `chunk`, дубликаты, пропуски и
  преждевременное завершение.
- Декодировать Base64 потоково, не накапливая весь CSV в RAM.
- Добавить таймаут, отмену и обработку потери UART.
- Возобновлять обычную обработку telemetry после последнего чанка или ошибки.
- Не считать штатную паузу telemetry во время `GET_LOG` потерей соединения.

### 2. Backend REST API

Добавить защищённые endpoint-ы:

- `GET /rest/logs` — получить список доступных логов;
- `GET /rest/logs/{processId}` — скачать CSV выбранного процесса.

Требования:

- разрешать только числовой идентификатор процесса;
- не принимать произвольные имена файлов;
- исключить path traversal;
- возвращать корректный `Content-Type` и имя CSV-файла;
- преобразовывать ошибки контроллера в понятные HTTP-ошибки;
- не блокировать основной цикл управления во время скачивания.

Предпочтительный вариант реализации — потоковая передача декодированных
данных клиенту с небольшим буфером. Если ограничения используемого HTTP
стека не позволят это сделать, можно временно сохранять файл в LittleFS и
удалять его после завершения HTTP-ответа.

### 3. Telemetry и совместимость

- Добавить `preempt_cnt` в `RectificationProcess::Metrics`, snapshot, REST,
  MQTT и другие каналы, где публикуется telemetry.
- Использовать существующую обработку `common.cfg_chgd` для автоматического
  обновления настроек.
- Добавить `tts` в backend-модель telemetry, если UI должен показывать таймер
  сохранения настроек.
- Добавить проверку минимальной версии API перед доступом к журналам.
- Закрыть backlog совместимости со спецификацией v1.9:
  - заменить boolean-модель `formula` на значения `0|1|2`;
  - добавить `predec`;
  - добавить `extended_heads`;
  - обновить сериализацию, десериализацию и обработчики `SET`.

## План frontend

### 1. Типы и API-клиент

Добавить типы:

- `LogFile`;
- `LogListResponse`;
- `LogTransferStart`;
- `LogChunk`;
- `LogTransferError`;
- `preempt_cnt` в telemetry;
- `cfg_chgd` и `tts` в `common`.

Добавить API-функции:

- получение списка логов;
- скачивание одного лога;
- отмена или повтор скачивания при необходимости.

### 2. Экран журналов

Добавить раздел «История ректификаций»:

- список файлов с номерами процессов;
- выбор файла;
- запуск скачивания;
- прогресс `chunk / total`;
- состояния загрузки, завершения, отмены и ошибки;
- автоматическое сохранение CSV через браузер;
- понятные сообщения для ошибок SD-карты и отсутствующего файла.

Кнопку скачивания следует блокировать, если контроллер не находится в
дежурном режиме или версия API не поддерживает `GET_LOG`.

### 3. Telemetry и настройки

- Показывать `preempt_cnt` на этапе «Тело» как диагностический показатель
  работы автоматики.
- Показывать `cfg_chgd` как состояние «настройки изменены на контроллере» и
  автоматически обновлять настройки.
- Показывать `tts` как время до сохранения настроек в энергонезависимую память.
- Использовать существующий version guard для новых возможностей.
- В рамках backlog v1.9:
  - заменить toggle `formula` на выбор режима `0`, `1`, `2`;
  - добавить UI для `predec`;
  - добавить UI для `extended_heads`;
  - обеспечить сохранение новых полей в профилях и мастере запуска;
  - мигрировать старые boolean-профили.

## План тестирования

### Native и embedded

- Формирование `GET_LOG` и `GET_LOG <номер>`.
- Разбор ответов `LIST` и `START`.
- Разбор `type: "file"` и Base64-декодирование.
- Пустой, короткий, полный 600-байтный и последний неполный чанк.
- Проверка последовательности чанков, пропуска, дубликата и неверного `total`.
- Завершение передачи по `chunk == total`.
- Таймаут, отключение UART и восстановление telemetry.
- Все коды ошибок `err_num`, `err_mnt`, `err_nf`, `err_int`.
- Проверка ограничения размера UART-пакета.
- Разбор `preempt_cnt` в telemetry `hearts`.

### REST и интеграционные тесты

- Получение списка логов.
- Полное скачивание CSV и проверка содержимого.
- Корректные заголовки и имя скачиваемого файла.
- Преобразование ошибок контроллера в HTTP-ответы.
- Запрет скачивания при неподдерживаемой версии API.
- Отсутствие смешивания двух параллельных transfer-сессий.
- Сценарий: список → выбор процесса → скачивание → проверка CSV.

### Frontend

- Отображение списка файлов.
- Прогресс и завершение загрузки.
- Ошибка, отмена и повторная попытка.
- Отображение `preempt_cnt`, `cfg_chgd` и `tts`.
- Version guard для старого контроллера.
- Миграция старых boolean-значений `formula`.
- Сохранение и загрузка `predec` и `extended_heads` в профилях.

## Пользовательский сценарий

Добавить экран «История ректификаций». После завершения процесса пользователь
открывает список логов, выбирает номер процесса и скачивает CSV. В карточке
процесса можно показать `preempt_cnt`, давление, температуры и события, чтобы
понять причины снижения скорости отбора, сравнить партии и скорректировать
профиль следующей ректификации.

## Проверки перед реализацией

Перед началом разработки необходимо зафиксировать:

1. минимальную версию firmware/API, на которой доступен `GET_LOG`;
2. способ потоковой передачи CSV через используемый HTTP-стек;
3. допустимое поведение при остановке или отмене загрузки;
4. необходимость сохранения промежуточного файла после перезагрузки
   OpenConnect.
