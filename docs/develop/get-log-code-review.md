Объект анализа — текущий рабочий код, не только изменения последнего коммита. Номера строк относятся к нему.
Выполнен статический анализ. Прошивка, браузер на устройстве, сборки и тесты не запускались. Код не исправлялся, коммиты не создавались.
P1 — блокирует скачивание/надёжность передачи; P2 — нарушает восстановление, отмену или диагностику.
«Подтверждено» означает наличие дефекта в логике; связь с конкретным наблюдением требует трассы, если указано отдельно.

### Компактное ТЗ для агента: решения

**Статус:** план реализации, не выполненные исправления. Текущая задача — только документирование; применять кодовые изменения после отдельного поручения. Не делать коммиты, сборки, установки или аппаратные проверки без разрешения. Существующие пользовательские изменения сохранить.
**Чтение:** для реализации достаточно этого раздела, карты файлов ниже и затрагиваемых функций. Полное ревью читать только при спорном пункте. Номера строк ниже — ориентиры; искать по символам. Не исследовать весь репозиторий заново.
**Цель:** одна UART-сессия GET_LOG, быстрый RX, явное завершение/ошибка/отмена, повторно доступный CSV. Не добавлять WS, CRC/EOF или менять формат UART. Причину первого отказа малого файла не считать установленной.

**1. F1/F2/F4 — исправить клиентский жизненный цикл (`Client`, `UI`).**
- Заменить boolean старта на результат с вариантами: `accepted` (202 + статус), `ready` (200 `text/csv` + Blob), `error` (HTTP status + backend code/message). Эти имена — предлагаемые, не существующие API.
- При `ready` сохранить Blob сразу; polling не запускать. При `accepted` опрашивать последовательно с интервалом 500 мс; удалить лимит 30 попыток.
- Timeout ожидания считать от последнего изменения состояния или увеличения `received`, не от последнего успешного HTTP. Предлагаемый клиентский idle timeout — 15 с при текущем backend timeout 10 с; GET статуса ограничить 5 с. Получение тела CSV ограничить отдельно, например 60 с. Это начальные значения, не свойства UART-контракта.
- Для каждого fetch использовать AbortSignal; сохранять HTTP/backend ошибки, не превращать их в null/false. Если общий `apiFetch` нужен другим функциям, менять только GET_LOG-путь, без глобального изменения поведения клиента.
- Локальный UI-статус отделить от backend snapshot: `starting/waiting/downloading/done/error/cancelled`. При timeout/ошибке завершить локальное ожидание; ошибка должна отображаться раньше старого `receiving`.
- После каждого await проверить поколение операции и состояние отмены, в том числе после получения Blob и перед нажатием ссылки. При новом действии очищать старую ошибку; при уходе со страницы отменять локальные запросы.
- **Готово:** стартовый 200 сохраняется один раз; передача >30 опросов завершается скачиванием; зависший HTTP ограничен; ошибка видна, старое продолжение не сохраняет файл.

**2. B2/B1/B3 — согласованная сессия (`Protocol`, `Queue`, `REST`).**
- Использовать один общий mutex сессии вместо широкого архитектурного рефакторинга. Защитить все чтения/переходы/контейнеры Transfer; HTTP получает snapshot по значению, не ссылки. Большой CSV отдавать через отдельный стабильный объект результата, не копировать под mutex на каждом status GET.
- Не держать mutex во время UART/HTTP/FS ожидания, callback или enqueue. Резервировать под lock, отпустить, поставить команду, при отказе откатить только тот же generation. Queue перед отправкой проверяет generation и допустимое состояние.
- Разделить состояния: `IDLE`, `QUEUED_LIST`, `WAITING_LIST`, `LIST_RECEIVED`, `QUEUED_FILE`, `WAITING_START`, `RECEIVING`, `COMPLETED`, `ERROR`, `DRAINING`. Названия внутренние; JSON-схему изменять согласованно с Client/UI.
- Атомарно записывать `generation`, вид запроса и process id ДО enqueue. Активный запрос того же файла возвращает текущий статус без повторного enqueue; другого файла — 409. Имя из START не заменяет зарезервированный process id.
- Queue больше не вызывает безусловный `beginFile/reset` для уже зарезервированного запроса. Переход в WAITING_START/WAITING_LIST выполнить ДО записи UART; учитывать отказ записи.
- При enqueue=false вернуть 503 с `queue_full`, убрать резерв. Для очереди/ожидания LIST/START ввести отдельные deadline; исходная точка — резервирование/отправка соответственно. Предлагаемый предел каждого ожидания — 10 с; timeout должен проверяться независимо от HTTP polling.
- После отправки GET_LOG не отправлять обычные команды до завершения либо окончания DRAINING. Не ждать терминального состояния в блокирующем цикле: worker продолжает обслуживание, но откладывает обычную отправку. Аварийные команды не блокировать новой политикой молча; сохранить существующий safety-путь, при прерывании файла перейти к дренированию.
- **Готово:** два клиента создают одну команду; enqueue=false не оставляет busy; потерянные LIST/START заканчиваются ошибкой; snapshot/reset/consume не гоняются; обычные запросы не вклиниваются в файл.

**3. T1/T2/T3/T4 — отделить RX файла от телеметрии (`Connector`, `Protocol`).**
- После разбора JSON сначала классифицировать GET_LOG/LIST/START/file и передать в Transfer; только обычную телеметрию отправлять через `lastMessage` и общий telemetry mutex. Файловые кадры не должны ждать этот mutex, сетевые callback или подробный лог всего payload.
- Не запускать GET_SETTINGS/VERSION при восстановлении связи во время зарезервированного/активного/дренируемого GET_LOG: отложить их до освобождения UART-транзакции.
- Не использовать `logTransferActive`, вычисленный до блокирующего чтения, для финального delay/учёта ошибок. Брать актуальный snapshot после кадра; при backlog продолжать RX без фиксированной покадровой паузы. При непрерывном потоке оставить короткие ограниченные проходы/уступку планировщику, не делать busy spin.
- Удалить flush по `buffered >4096`: это не overflow ring 8192. Подключить обработку реальных UART overflow/buffer-full событий без второго потребителя RX; ошибку записать в сессию, последующее восстановление выполнять в DRAINING, не как успешное завершение.
- Держать line accumulator между короткими чтениями. Полный JSON разбирать только после `\n`; учитывать `\r\n`. Размер 1024 оставить, последнюю позицию зарезервировать под NUL.
- Внутри ожидания проверять deadline кадра и сессии. Deadline кадра — от первого байта, не продлевается новыми байтами; стартовое значение 5 с. Для RECEIVING сохранить 10 с без валидного прогресса; повреждённые/посторонние байты его не продлевают.
- При oversize дренировать до следующего `\n`, не парсить хвост отдельно. При invalid JSON/обрыве ожидаемого файлового кадра выставить явную ошибку и перейти к восстановлению RX; вне файловой сессии не превращать произвольный плохой JSON в GET_LOG-error.
- Проверять результат consume вместе с состоянием: `false` может означать посторонний кадр, а не ошибку; ERROR самого парсера не затирать общей ошибкой. Сохранить проверки порядка чанков и завершение по `received == total`.
- **Готово:** файл принимается при занятости telemetry mutex; backlog не выбрасывается; START не вызывает старую паузу 500 мс; oversize/нет newline/битый финальный JSON дают ограниченное восстановление и конкретный error code.

**4. B4 — отмена без возрождения сессии (`Protocol`, `Queue`, `REST`, `UI`).**
- Queue-команды маркировать generation; DELETE инвалидирует её. Worker пропускает отменённый запрос перед отправкой. Проверку отмены и решение начать отправку согласовать: если отправка уже началась, считать запрос отправленным и дренировать.
- До отправки отмена освобождает резерв; после отправки — DRAINING вместо reset в IDLE. Не принимать поздний START как новый запрос и не записывать старые чанки в новый результат; блокировать новый GET_LOG/LIST до восстановления границы старого потока.
- В DRAINING читать и отбрасывать только кадры старой передачи; использовать известный финальный чанк, возобновившуюся телеметрию или проверенное условие восстановления. Не путать backend generation с UART session id: контроллер не возвращает этот generation.
- Одна произвольная пауза тишины не доказывает конец старой передачи. Если надёжный признак не найден, оставить явный recovery-required/busy, а не объявлять безопасную изоляцию; критерий повторного допуска проверить по протоколу/трассе устройства.
- UI сначала инвалидирует локальное поколение и abort запросы, затем учитывает ответ DELETE. Отказ отмены показывать явно; не вызывать GET с побочным запуском LIST сразу после отмены.
- **Готово:** отменённая queued-команда не отправляется; поздний START не возрождает операцию; старая HTTP-операция не сохраняет Blob; новый запрос не смешивается с недренированным UART-потоком.

**5. F3 — явное обновление списка и чистый status (`REST`, `Client`, `UI`).**
- Минимальный совместимый вариант: добавить к существующему GET `/rest/logs` режимы `statusOnly=1` (только snapshot) и `refresh=1` (явный запрос списка). Это предлагаемые параметры; существующий GET без параметров оставить совместимым.
- UI polling файла/списка использует только statusOnly. Кнопка «Обновить» вызывает refresh один раз, затем ждёт LIST_RECEIVED/ERROR с deadline; в активной файловой сессии refresh возвращает 409 без reset.
- Refresh разрешён из IDLE/LIST_RECEIVED/ERROR, если UART уже безопасно освобождён. Повторный refresh при активном запросе списка возвращает его статус, не ставит дубликат. Снимать pending на успехе, отказе enqueue и timeout.
- Проверять доступную актуальную стадию перед запросом; если данных стадии нет, не изобретать её, а передавать явную ошибку контроллера. UI не должен маскировать её под пустой список.
- **Готово:** первый клик показывает поздно пришедший список; повторный клик действительно обновляет его; ERROR не блокирует восстановление; чтение статуса не запускает UART-команд.

**6. B5 — безопасный Base64 (`Protocol`).**
- Заменить signed accumulator на ограниченный unsigned или декодирование группами по 4 символа. Валидировать алфавит, позицию/число padding и длину; не принимать повреждённый чанк как успешный.
- Сохранить побайтовый CSV, лимит итогового размера и существующую проверку последовательности чанков. Не менять UART-контракт и не требовать CRC.
- **Готово:** 600 разнообразных байт восстанавливаются точно; padding для остатков 1/2 байта корректен; плохая Base64 даёт invalid_data. Sanitizer/C++14 проверку выполнять только при разрешённом запуске.

**7. F2/H1 — результат не исчезает при HTTP GET (`Protocol`, `REST`).**
- Убрать reset результата до отправки CSV. Повторный GET того же completed process id отдаёт тот же CSV без новой UART-команды. Результат хранится до явной отмены/замены новой принятой операцией; HTTP-ответ удерживает его ресурс до окончания/обрыва отправки.
- Не возвращать ссылки на mutable string после освобождения lock и не копировать весь CSV одновременно в несколько строк. Metadata snapshot отделить от ресурса результата; удалить ресурс только после освобождения всех активных HTTP-читателей.
- H1/OOM не объявлять доказанным. Перед выбором хранения установить доступное heap/PSRAM/FS и механизм streaming текущего HTTP-сервера; не добавлять FS/PSRAM вслепую. Если измерения запрещены, отметить решение по памяти как неподтверждённое.
- При подтверждённом недостатке RAM использовать доступное временное хранилище с bounded буферами и потоковой выдачей. Проверять открытие, каждую запись, общий лимит и чтение; при отказе явный storage_error, не COMPLETED. Медленные FS-записи не переносить прямо в RX без оценки задержек; при необходимости ограниченная очередь writer с явным backpressure-error, не молчаливая потеря чанков.
- **Готово:** обрыв HTTP не уничтожает completed; повтор отдаёт идентичные байты; отказ хранения не выдаёт частичный CSV как успешный. Пиковая память не растёт из-за дублирования полного файла; аппаратную проверку не подменять предположением.

**Порядок и минимальная приёмка:**
1. Client/UI (F1/F2/F4) → синхронизация/reservation/deadlines (B2/B1/B3) → RX (T1–T4) → cancel + list (B4/F3) → Base64 + lifetime/storage (B5/H1). Не смешивать с несвязанным рефакторингом.
2. Добавить targeted проверки: стартовые 200/202; >30 опросов; 1/599/600/601 байт; duplicate start; enqueue fail; lost LIST/START; cancelled generation; late START; invalid/oversize JSON; повтор CSV после обрыва HTTP. Сравнивать байты, не только boolean/HTTP status.
3. Без разрешения запусков: предоставить изменения/добавленные проверки и список непроверенных аппаратных условий. Не писать «исправлено на устройстве» или «тесты прошли» без фактического запуска.

### Главные выводы

- **Большой файл может успешно передаваться UART, но никогда не скачаться:** UI ограничен 30 опросами и после прекращения ожидания продолжает показывать `receiving` (F1).
- **Готовый CSV может быть выброшен стартовым запросом:** backend отвечает `200 text/csv`, frontend принимает только признак успеха, backend сбрасывает результат (F2).
- **В `_telemetry` действительно есть проблемы:** устаревший снимок состояния, блокирующая обработка каждого файлового кадра, недостоверная проверка переполнения и неполная обработка framing/таймаутов (T1–T4).
- Дополнительно нарушены резервирование передачи, межзадачная синхронизация, восстановление списка и отмена (B1–B4).
- **Нельзя утверждать, что F2 объясняет первое скачивание любого малого файла.** Из состояния `LIST_RECEIVED` старт обычно возвращает `202`, затем polling должен увидеть `completed`. Для этого случая нужны HTTP/UART данные.
- В проверенном компоненте нет графического спиннера: есть текст «Загрузка: received / total». Он использует REST polling, а не WebSocket. Если на устройстве отображается другой UI, проверить соответствие развёрнутого frontend этой ветке.

### F1. P1 — frontend бросает длинную передачу и скрывает ошибку

**Места:** `UI:57–79,118–122`; `Protocol:369–381`.
**Подтверждено:** всего 30 итераций с задержкой 500 мс плюс длительность HTTP, без продления при росте `received`. После выхода устанавливается `logError`, но `logStatus` остаётся `receiving`; эта ветка UI имеет приоритет над ошибкой. Дальнейших опросов и скачивания нет.
**Сценарий:** UART исправно работает дольше окна ожидания → frontend прекращает polling → backend позже получает последний чанк → CSV остаётся готовым, браузер его не запрашивает.
**Расчёт:** 200 KiB после Base64 требуют около 266,7 KiB передачи; при 115200/8N1 это минимум около 23,7 с даже без JSON и пауз. Окно из 30 коротких HTTP-опросов заведомо недостаточно для таких файлов.
**Исправление:** ждать по времени отсутствия прогресса, отдельно ограничивать каждый HTTP-запрос; явно завершать локальное состояние ожидания и показывать ошибку. Не подменять это простым увеличением числа попыток.

### F2. P1 — стартовый GET теряет уже готовый CSV

**Места:** `Client:292–299`; `REST:400–414`; `UI:53–62`.
**Подтверждено:** `startLogDownload()` возвращает boolean при успешном HTTP, не читая CSV. Backend при совпадающем готовом файле отдаёт CSV и делает `reset()`. Следующий status GET видит не `completed`, а сброшенную сессию и может запустить список.
**Сценарий:** файл остался готовым после F1, повторного захода или предыдущей попытки → первое нажатие забирает и выбрасывает CSV → UI бесполезно ожидает `completed`. Возможная гонка с быстрым завершением требует трассировки.
**Исправление:** различать `200 text/csv` и `202 application/json`, сохранять Blob сразу при 200. Альтернатива — разделить запуск передачи и получение результата; выдача результата должна поддерживать безопасный повтор после обрыва HTTP.
**Ограничение:** малый размер сам по себе не вызывает F2; это не доказанная универсальная причина отказа первого малого файла.

### T1. P1 — `_telemetry` использует устаревший режим передачи

**Места:** `Connector:185–194,238–256,326–327`; `Queue:212–229`.
**Подтверждено:** `logTransferActive` вычисляется один раз до блокирующего чтения строки. Между этим и концом итерации очередь может вызвать `beginFile()`, а `consume()` — завершить передачу. Задержка и учёт ошибок опираются на старое состояние.
**Сценарий:** цикл вошёл в чтение при false → другая задача запускает GET_LOG → читается START → применяется ещё 500 мс вместо быстрого чтения. За 500 мс при непрерывном 115200/8N1 поступает до 5760 байт; это ещё помещается в ring 8192, поэтому **одна такая пауза не доказывает потерю**, но резко сокращает запас на блокировки T2.
**Исправление:** определить единого владельца переходов; резервировать режим до UART-команды, после обработки кадра получать актуальный согласованный статус. При наличии RX backlog сразу продолжать чтение, не делать покадровую фиксированную паузу.

### T2. P1 — приём каждого файлового кадра зависит от общего mutex

**Места:** `Connector:258–283,312–313`; `lib/ssvcOpenConnect/core/rectification/RectificationProcess.cpp:305–329,675`; `Queue:256–274`.
**Подтверждено:** даже `type=file` сначала проходит логирование и ожидание общего mutex до 1000 мс для `lastMessage`, и только затем попадает в файловый парсер. Общий mutex используется обработчиком телеметрии и callback команд. При восстановлении связи до разбора START дополнительно ставятся GET_SETTINGS и VERSION.
**Влияние:** ring 8192 байта даёт примерно 0,71 с номинального запаса при непрерывном входе. Разрешённая секундная блокировка больше этого запаса; вместе с T1 возможна потеря кадра → `invalid_chunk`/`timeout`. Фактическая длительность удержания mutex и потеря на устройстве **не измерены**.
**Исправление:** маршрутизировать GET_LOG/file до общего mailbox телеметрии; не ожидать его mutex для записи файла. Отложить обычные восстановительные запросы до окончания/дренирования GET_LOG; сетевые публикации не должны блокировать RX-путь.

### T3. P2 — заполненность RX ошибочно трактуется как переполнение

**Места:** `Connector:49–51,189–195`; `SsvcConnector.h:89`.
**Подтверждено:** при backlog >4096 и режиме не RECEIVING вызывается `uart_flush()`, хотя установлен ring 8192. Это уничтожает накопленные данные, а не проверяет факт аппаратного переполнения. Очередь событий UART отключена (`kQueueSize=0`).
**Сценарий:** после отмены/ошибки контроллер досылает файл, либо скопился другой поток → следующий цикл выбрасывает и хвост файла, и следующие ответы/телеметрию. Возможен отказ следующего запроса списка с B3.
**Исправление:** читать backlog; переполнение обрабатывать по UART-событиям и переводить активную сессию в диагностируемую ошибку. При отмене дренировать старую сессию осознанно, а не удалять произвольный RX backlog вместе с новыми ответами.

### T4. P2 — timeout и восстановление границы строки неполны

**Места:** `Connector:195–229,231–256,281–283,312–313`.
**Подтверждено:** `checkTimeout()` вызывается только вне внутреннего чтения. Внутри ограничивается тишина после последнего байта, но не общая длительность неполного кадра. Любой новый байт продлевает чтение; при достижении 1023 байт строка обрывается без дренирования до `\n`. После 5 с тишины частичная строка разбирается/теряется; возврат `consume()` игнорируется.
**Сценарий:** повреждённая строка без `\n` и редкие байты чаще 5 с удерживают задачу значительно дольше 10-секундного timeout передачи. Невалидный JSON финального чанка не переводит Transfer в ошибку сразу: UI ждёт timeout. После сверхдлинного кадра хвост становится отдельным JSON-кандидатом. Ошибки самого Protocol, например invalid_data, напротив, уже устанавливают ERROR внутри consume().
**Исправление:** сохраняемый line accumulator, отдельные deadline кадра/передачи, проверки deadline внутри RX ожидания; на превышение длины — дренирование до разделителя, явная ошибка активной сессии. Различать ожидаемую тишину при GET_LOG и повреждение его кадра.
**Важно:** штатные JSON до 890/900 байт помещаются в 1024; увеличение этого буфера само по себе не исправляет описанные ошибки. T4 проявляется при нарушении framing/тайминга, не при обычном коротком кадре.

### B1. P1 — резервирование и сериализация UART-транзакции отсутствуют

**Места:** `REST:382–417`; `Queue:212–244`; `Protocol:223–232`.
**Подтверждено:** HTTP только ставит команду файла в очередь; до `beginFile()` состояние не меняется. Повторное нажатие/второй клиент ставят второй GET_LOG. Каждый `beginFile()` вызывает `reset()`. После UART-отправки очередь сразу переходит к следующей команде. До START имя файла пустое, поэтому REST разрешает запрос даже другого номера.
**Сценарий:** двойной клик или два клиента → вторая команда сбрасывает данные первой; также обычные команды могут отправляться во время GET_LOG. Реакция контроллера на такие команды не установлена, но отсутствие резервирования и повторные reset подтверждены.
**Исправление:** атомарно резервировать номер процесса и состояние QUEUED до enqueue, проверять его результат; тот же файл — статус без новой команды, другой — 409. Удерживать обычные запросы до терминального состояния; отдельно определить политику аварийных команд, не блокировать их бездумно.

### B2. P1 — общий `Transfer` не защищён от межзадачных гонок

**Места:** `Protocol:211–214,324–325,336–353,384–394`; `Connector:283,313`; `Queue:215–224`; `REST:326–345,382–421,437`.
**Подтверждено:** UART дописывает `std::string`, очередь/HTTP сбрасывают его, HTTP читает строки/вектор. Нет общей синхронизации этих операций; mutex в Connector защищает только `lastMessage`, не `Transfer`.
**Сценарий:** DELETE одновременно с `_data += decoded`, чтение списка одновременно с обновлением, копирование CSV одновременно с новой командой → гонки данных, риск повреждения памяти/неверных снимков.
**Исправление:** один владелец сессии и очередь сообщений или общий mutex с короткими критическими секциями. Отдавать согласованный snapshot, не ссылки на изменяемые контейнеры. Не держать этот lock во время HTTP/UART/FS ожиданий.

### B3. P1 — список может навсегда остаться pending; ошибки enqueue скрыты

**Места:** `REST:326–330,385–390,415–417`; `Protocol:216–220,369–381`; `Queue:462–470`.
**Подтверждено:** список остаётся `IDLE + pending`, timeout работает только для RECEIVING. При отсутствии ответа pending не снимается. REST игнорирует boolean `getLog()`; отказ очереди для списка оставляет установленный pending, для файла возвращается 202 без реально запущенной передачи.
**Сценарий:** потеря единственного LIST, переполненная очередь или отказ постановки → повторный список не запускается, файлы получают 409 busy либо клиент ждёт операцию, которой нет.
**Исправление:** WAITING_LIST/QUEUED со своими deadline; проверка enqueue и откат резерва при отказе; возвращать явную HTTP ошибку. Терминальные ошибки должны разрешать контролируемый повтор.

### B4. P2 — отмена не изолирует старую сессию

**Места:** `REST:432–440`; `Protocol:262–286,302–314`; `Queue:212–230`; `UI:59–69,82–89`; `Client:316–318`.
**Подтверждено:** DELETE делает только reset. Неотправленная команда остаётся в очереди; поздний START снова принимается даже из IDLE. UI игнорирует false отмены и сразу читает статус: этот GET может начать новый список. Проверка requestId находится только до `fetchLogStatus()`, не после последующих await.
**Сценарий:** отмена до отправки → GET_LOG всё равно начинается; отмена и новый запрос → старые чанки попадают в новую сессию; отмена во время HTTP получения → старое продолжение может всё равно инициировать сохранение.
**Исправление:** отменять неотправленную команду; отправленную сессию дренировать до завершения/тишины, не принимая поздний START как новую. На frontend — проверять поколение после каждого await, отменять HTTP-запросы, учитывать отказ DELETE. Один frontend requestId не может различить старые UART-пакеты без поддержки backend.

### B5. P2 — декодер Base64 использует неограниченный signed аккумулятор

**Место:** `Protocol:95–115`.
**Подтверждено для C++14:** `int accumulator` сдвигается на 6 на каждом символе, старые биты не убираются. На обычных длинных ненулевых данных значение выходит за допустимые условия signed left shift/становится отрицательным; следующий сдвиг приводит к undefined behavior. Прочитанная `compile_commands.json:3–15` содержит native `-std=gnu++14`; стандарт конкретной ESP-сборки не установлен.
**Влияние:** потенциально неверный CSV, не гарантированный отказ каждой передачи. Тест длинных нулевых данных не выявляет этот дефект.
**Исправление:** unsigned ограниченный аккумулятор или декодирование четвёрками, корректная проверка padding. Проверять штатный 600-байтовый чанк с разнообразными байтами и sanitizers на C++14.

### F3. P2 — список не ожидается и плохо восстанавливается после ошибок

**Места:** `UI:39–45`; `REST:326–345`.
**Подтверждено:** «Обновить» делает один GET. Первый ответ часто IDLE, поздний LIST сам не отобразится. В ERROR/LIST_RECEIVED повторный GET не запускает свежий список; `loadLogs()` не очищает старый `logError`.
**Исправление:** отделить явное обновление списка от чистого статуса, ждать LIST/ошибку с deadline; очищать локальную ошибку при новом действии. Проверять актуальную дежурную стадию или возвращать явную причину отказа: UI сейчас проверяет API, но не стадию (`UI:16–22`, спецификация `:992`).

### F4. P2 — HTTP ошибки теряются, продолжения не ограничены временем

**Места:** `Client:287–299,369–392`; `UI:53–79`.
**Подтверждено:** ошибки status превращаются в null, старта — в false, backend коды не доходят до UI; `apiFetch()` сам ловит исключения, поэтому catch в `loadLogs()` их не увидит. Нет AbortSignal/таймаута fetch; лимит итераций не ограничивает зависший HTTP-запрос.
**Исправление:** сохранять HTTP статус и error code, различать busy/ошибку сети/ошибку контроллера. Ограничивать каждый запрос и корректно завершать локальный индикатор при отказе.

### H1. P1 — память и выдача больших CSV: риск, требующий измерения

**Места:** `Protocol:16,318–325`; `REST:406–412`.
Весь файл накапливается в `std::string`, затем копируется в `String csv` до reset; возможны дополнительные расходы HTTP-ответа. Лимит 512 KiB не доказывает наличие свободного блока heap. Проверки успешности полного копирования перед отправкой нет; результат сбрасывается ещё до доставки HTTP тела.
**Степень уверенности:** копирование/ранний reset подтверждены; OOM, число внутренних копий и роль PSRAM не проверены. Это не установленная причина жалобы.
**Исправление:** bounded-приём во временное файловое хранилище и потоковая выдача с корректным временем жизни; либо проверяемое выделение подходящей памяти. Не удалять единственный результат до возможности безопасного повторного HTTP получения. Проверить heap/free largest block на росте и выдаче.

### Что не следует объявлять причиной без проверки

- 1024-байтовый line buffer не меньше штатного GET_LOG JSON; кадры завершаются NUL. Base64 CSV не содержит буквальных переносов внутри `data`.
- Отсутствие отдельного EOF/CRC не противоречит найденной спецификации. При корректном START и единственном финальном чанке завершение уже реализовано.
- Отсутствие WS события готовности не ломает данный UI: он ожидает REST статус. Добавление WS не устраняет ошибки сессий и выдачи.
- Немедленный `URL.revokeObjectURL()` в `UI:69` — дополнительный браузерный кандидат на проверку, не доказанная основная причина.
- Диагностика редактора о `ArduinoJson.h`/ESP идентификаторах не является доказательством runtime-сбоя GET_LOG. Найденная база компиляции относится к native; корректность embedded toolchain этим ревью не проверялась.

### Предлагаемый порядок исправления

1. F1/F2/F4: ожидание по прогрессу, корректный 200 CSV, явные ошибки/терминальные состояния UI.
2. B1/B2/B3/B4: единая сессия с номером процесса, резерв до enqueue, deadline очереди/списка, безопасная отмена и синхронизация.
3. T1–T4: быстрый RX без общего mailbox lock, актуальный режим, framing и диагностируемые UART ошибки. Простое увеличение delay/buffer не решает контракт.
4. B5/H1: безопасный Base64 и bounded-хранение/потоковая выдача, проверяемая сохранность результата.
Вариант минимального REST изменения — сохранять готовый CSV из стартового GET; более ясный контракт — отдельные запуск, чистый статус, выдача результата и отмена. Это предложения, не внесённые изменения.

### Проверки для подтверждения на устройстве и будущие регрессионные тесты

- Зафиксировать deployed frontend/firmware, API ≥1.10 и дежурный режим. Для первого малого файла снять последовательность GET: статус/Content-Type, START.total, все chunk, достижение completed, повторный GET CSV, размер Blob/сохранение. Не включать заголовки авторизации в отчёт.
- Размеры 1–599, 600, 601 байт; один/два чанка; длинные ненулевые Base64; отдельно уточнить контракт пустого файла (`START.total=0` сейчас отвергается).
- Передача >15 с с непрерывным ростом received; файл около 200 KiB и около лимита 512 KiB: polling до завершения, побайтовое сравнение CSV с оригиналом.
- UART backlog при запуске, искусственная занятость общего mutex, задержки планировщика: логировать длительность обработки кадра, occupancy и UART overflow, а не только JSON error.
- Пропуск/повреждение START, среднего и последнего чанка, отсутствие `\n`, редкие байты, тишина: явная причина отказа и ограниченное время восстановления.
- Двойной клик/два клиента, очередь заполнена, потерян LIST, команды восстановления связи во время файла: один GET_LOG на сессию, без повторного reset.
- Отмена до enqueue/после START/во время HTTP; немедленный новый запрос; поздний START/чанки: старая операция не возрождается и не завершает новую.
- Стартовый `200 text/csv` после уже готового результата; обрыв доставки CSV и повтор: файл не выброшен и доступен повторно.
- HTTP 401/409/500, отсутствующий ответ, смена страницы: ошибка видна, запросы прекращены; сравнить отображаемый «спиннер» с проверенным компонентом.
Существуют `test/native/test_ssvc_log_protocol/test_main.cpp:11–170` и `interface/tests/unit/api/ssvcApi.logs.test.ts:39–135`. Они проверяют изолированный парсер/клиент, но не сквозной жизненный цикл. Тест start 200 сейчас проверяет только boolean, а не сохранение CSV. Нужны компонентные, UART-интеграционные и конкурентные сценарии выше; в рамках ревью они не запускались.
