# API Команд

Этот раздел описывает постановку команд для контроллера SSVC и отслеживание их
судьбы.

Команда не выполняется внутри HTTP-запроса: она попадает в очередь
`SsvcCommandsQueue` и уходит в UART отдельной задачей-воркером. Поэтому `200` на
`POST /rest/commands` означает **«принято в очередь»**, а не «выполнено».
Узнать, что произошло дальше, можно по `commandId` через
`GET /rest/commands/{id}`.

> Важно: в UART-протоколе SSVC у команды нет идентификатора и нет надёжной
> корреляции ответа с запросом (один воркер, общий бит успеха `BIT9`, эхо
> `request` перезаписывается следующим кадром). Поэтому `commandId` — это
> **идентификатор попытки в прошивке**, а не подтверждение выполнения на
> контроллере.

---

## Выполнение команды

**Эндпоинт:** `POST /rest/commands`

**Метод:** `POST`

**Аутентификация:** Требуется (`IS_AUTHENTICATED`)

### Тело запроса

JSON-объект. Имя команды — в поле **`commands`** (именно так, множественное
число); `parameters` необязателен и учитывается, только если это строка:

```json
{
  "commands": "start",
  "parameters": ""
}
```

Допустимые имена (`SsvcCommandsQueue::COMMAND_MAP`):

| Имя | Что делает | Ответ ожидается |
|---|---|---|
| `start` | `START` — старт процесса | не всегда |
| `stop` | `STOP` — остановка | не всегда |
| `pause` | `PAUSE` | да |
| `resume` | `RESUME` | не всегда |
| `next` | `NEXT` — переход к следующей стадии | не всегда |
| `at` | `AT` | да |
| `version` | `VERSION` — версия SSVC | да |
| `get_settings` / `settings` | `GET_SETTINGS` — перечитать настройки | да |
| `status` | `STATUS <текст>` — сообщение на дисплей SSVC (до 15 символов) | да |
| `set` | `SET <параметры>` — изменить настройки | да |
| `get_log` | получить журнал (`parameters` — номер процесса или пусто) | нет (сессия журнала) |
| `emergency_stop` | `STOP` вне общего FIFO, с новым поколением safety | не всегда |

Имена, параметры и allowlist — прежние; поведение кодов `400/409/501/503` не
менялось.

### Пример запроса (curl)

```bash
curl -X POST http://DEVICE_IP/rest/commands \
     -H "Authorization: Bearer YOUR_AUTH_TOKEN" \
     -H "Content-Type: application/json" \
     -d '{"commands":"start"}'
```

### Ответ `200 OK`

`200` **всегда** отдаётся как `application/json`:

```json
{
  "status": "accepted",
  "command": "start",
  "commandId": 42
}
```

Если предохранитель XKC-25 вернул неблокирующие предупреждения (только для
`start`), добавляется поле `warnings`:

```json
{
  "status": "accepted",
  "command": "start",
  "commandId": 43,
  "warnings": ["XKC-25: датчик не откалиброван, старт разрешён"]
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `status` | string | Всегда `"accepted"` — команда принята в очередь |
| `command` | string | Имя команды из запроса |
| `commandId` | uint32 | id записи журнала попыток для `GET /rest/commands/{id}` |
| `warnings` | string[] | Только если XKC-25 вернул предупреждения |

`commandId` назначается в той же критической секции, что и фактическое принятие
в очередь (`SsvcCommandsQueue.cpp:956-970`), и возвращается только этой
постановке — это не «последний принятый id», поэтому параллельные POST из HTTP,
MQTT и ботов не перепутают идентификаторы.

Особый случай: `commandId: 0` означает «новой записи нет». Так отвечает
повторный `get_log` на уже зарезервированную сессию (та же передача, новой
UART-команды нет). `GET /rest/commands/0` вернёт `404`.

### Коды ошибок

| Код | Content-Type | Тело | Условие |
|---|---|---|---|
| `200` | application/json | `{"status":"accepted","command":"…","commandId":N[,"warnings":[…]]}` | принято в очередь |
| `400` | text/plain | `Invalid JSON format` | тело не JSON-объект |
| `400` | text/plain | `Missing or invalid 'commands' field` | нет строкового `commands` |
| `401` | — | пусто | нет токена/не тот пользователь |
| `409` | application/json | `{"status":"rejected","command":"start","blockReasons":[…]}` | предохранитель XKC-25 в режиме block |
| `409` | text/plain | `Command unsupported by device API` | возможности нет на этой версии API |
| `501` | text/plain | `Command not implemented` | имени нет в `COMMAND_MAP` |
| `503` | text/plain | `Command queue is full` | не удалось поставить в очередь |
| `503` | text/plain | `Command not accepted` | прочие отказы постановки |
| `500` | text/plain | `Command execution failed` | исключение |

При отказе `commandId` не выдаётся (тела ошибок не менялись), но запись с
состоянием `rejected` и причиной остаётся в журнале для диагностики.

## Судьба команды

**Эндпоинт:** `GET /rest/commands/{id}`

**Метод:** `GET`

**Аутентификация:** Требуется (`IS_AUTHENTICATED`)

`{id}` — значение `commandId` из ответа `POST /rest/commands`. Путь
регистрируется как `/rest/commands/*` (prefix-матчер с базой
`/rest/commands/`), поэтому `POST /rest/commands` не задевается, а
`GET /rest/commands/` с пустым id даёт `400`. Завершающего слеша в базе нет —
`/rest/commands/` и `/rest/commands` — разные пути.

### Пример запроса (curl)

```bash
curl -X GET http://DEVICE_IP/rest/commands/42 \
     -H "Authorization: Bearer YOUR_AUTH_TOKEN"
```

### Ответ `200 OK`

```json
{
  "id": 42,
  "command": "start",
  "state": "sent",
  "queued_at": 123456,
  "started_at": 123470,
  "finished_at": 126500,
  "ok": null,
  "reason": null,
  "confidence": "transport"
}
```

| Поле | Тип | Смысл |
|---|---|---|
| `id` | uint32 | id записи (монотонный счётчик, начинается с 1) |
| `command` | string | Каноническое имя команды (`settings` нормализуется в `get_settings`, `emergency_stop` — отдельное имя) |
| `state` | string | `queued` \| `running` \| `sent` \| `done` \| `rejected` \| `timeout` |
| `queued_at` | uint32 | `millis()` момента принятия в очередь |
| `started_at` | uint32 \| null | `millis()` момента, когда воркер взял команду |
| `finished_at` | uint32 \| null | `millis()` терминального состояния |
| `ok` | bool \| null | `true` — пришёл бит успеха; `false` — отказ/таймаут; `null` — исход неизвестен (например `sent`) |
| `reason` | string \| null | Причина для `rejected`/`timeout`/прерывания (см. ниже) |
| `confidence` | string | Всегда `"transport"` |

### Состояния и переходы

| Состояние | Когда | Где в коде |
|---|---|---|
| `queued` | команда принята в очередь (запись создаётся до `xQueueSend`, id выдаётся там же) | `SsvcCommandsQueue.cpp:956-970`, `:1041-1056`; `emergency_stop` — `:281-296` |
| `running` | воркер забрал команду и начал работу (после проверок generation/safety и откладывания на время лог-сессии) | `SsvcCommandsQueue.cpp:458` |
| `sent` | байты успешно записаны в UART (не терминальное состояние, попытки могут продолжаться) | `SsvcCommandsQueue.cpp:573` |
| `done` | пришёл ожидаемый бит и callback подтвердил успех (`ok:true`) | `SsvcCommandsQueue.cpp:680` |
| `rejected` | отказ на постановке: `invalid_parameters`, `no_supported_params`, `feature_unsupported`, `not_ready`, `queue_full`, `safety_rejected` | `SsvcCommandsQueue.cpp:875,898,927,936,964-969`, `:1079-1090`; `emergency_stop` — `:290-295` |
| `rejected` | отказ уже после отправки: `device_rejected` (SSVC ответил `result != OK`, бит `BIT1`), `invalid_response` (бит пришёл, но ответ не разобран), `uart_write_failed` (ни одна запись в UART не удалась), `cancelled_before_send` / `stale_after_emergency_stop` (команда снята до отправки) | `SsvcCommandsQueue.cpp:424,435,682,686,690` |
| `timeout` | попытки исчерпаны, ответа нет (`reason:"no_response"`) | `SsvcCommandsQueue.cpp:695` |
| `sent` (итог) | ответа может не быть вовсе — `START`/`NEXT`/`RESUME`/`STOP`/`GET_LOG`: остаётся честное «отправлено, ответа не ждём» (`reason:null`); прерванная аварийной командой — `reason:"preempted_by_safety"` | `SsvcCommandsQueue.cpp:579,677,693` |

Терминальные состояния: `done`, `rejected`, `timeout`, а также `sent` как
итоговое (у него заполнен `finished_at`).

Политика ретраев не менялась: повторяются только идемпотентные типы, а
`START`/`NEXT`/`RESUME` после неоднозначной отправки не повторяются вовсе —
именно поэтому их итог `sent`, а не `timeout`.

### Почему `confidence: "transport"`

Это уверенность в **транспорте**, а не в **выполнении**:

* `sent`/`done` означают «байты записаны в UART» и «пришёл бит успеха», а не
  «SSVC применил команду». Контроллер может ответить `OK` и не выполнить
  команду, а может выполнить и не ответить.
* `BIT9` взводится любым ответом с `result:"OK"`, поэтому при двух командах
  подряд ответ может быть засчитан не той команде, которая его ждала.
  Прошивка дополнительно сверяет глагол поля `request` с типом команды, но это
  только отсекает явно чужие ответы, а не даёт полной корреляции.
* Для `START`/`NEXT`/`RESUME`/`STOP`/`GET_LOG` ответа может не быть вовсе;
  `GET_LOG` завершается в `SsvcLogProtocol` и в журнале навсегда остаётся
  `sent`.

Семантическое «команда выполнена» потребовало бы эхо-номера в UART-протоколе
SSVC (`SET #42 …`), чего в текущей прошивке нет.

### Коды ошибок

| Код | Тело | Условие |
|---|---|---|
| `400` | `{"error":"invalid_id"}` | id пустой, со знаком/пробелом или содержит нецифровые символы |
| `401` | пусто | нет токена/не тот пользователь |
| `404` | `{"error":"not_found"}` | записи нет, она вытеснена кольцом или истёк TTL |

### Журнал попыток: память, TTL, переполнение

* Кольцо на **16** записей, статический массив в `SsvcCommandsQueue`
  (≈1.5 КБ `.bss`), без динамической памяти; параметры усечены до 64 байт.
* TTL — **10 минут** по `millis()`: после этого `GET` отвечает `404`, даже если
  слот ещё не перезаписан.
* При переполнении кольца перезаписывается самая старая запись — `GET` по её id
  вернёт `404`, а не чужую команду. Поэтому опрашивать судьбу нужно в пределах
  TTL и не рассчитывать на историю длиннее 16 команд.
* Журнал защищён отдельным мьютексом, который не удерживается во время
  UART-операций: запись обновляется до/после отправки, а не внутри неё.
* `lastRejectionReason` и политика ретраев не менялись — журнал их не заменяет.

## Ограничения, которые нужно знать клиенту

1. **`done` ≠ «применено»**. Максимум, что можно утверждать: «байты ушли и на
   команду пришёл ответ с успехом».
2. **Две команды подряд**. Если SSVC пришлёт запоздавший ответ на первую
   команду, он может быть засчитан второй (общий `BIT9`, один воркер,
   перезаписываемое эхо). В журнале это будет выглядеть как `done` у второй
   команды; различить это по REST нельзя.
3. **`START`/`STOP`/`NEXT`/`RESUME` могут не ответить**. Для них нормальное
   конечное состояние — `sent`, а не `done` и не `timeout`. Не считайте `sent`
   ошибкой.
4. **Записи `rejected` не адресуемы**: при отказе постановки `POST` возвращает
   прежние `4xx/5xx` без `commandId`, поэтому id такой записи клиенту
   неизвестен; она остаётся в журнале только для диагностики.
5. **Журнал не переживает перезагрузку** и не является аудитом: это окно
   «узнать судьбу» на время одного UI/MCP-раунда.
