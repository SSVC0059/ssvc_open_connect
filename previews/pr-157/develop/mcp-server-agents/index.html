    MCP-сервер: разбивка на пакеты работ для независимых агентов

    Документ-задание для параллельной разработки. Дополняет mcp-server.md: там — зачем, что и на каком API; здесь — кто, в каких файлах и с какими контрактами делает, чтобы пакеты можно было выполнять независимо и собрать без переписывания.

    Реализация не начата. Ниже — спецификация, готовая к запуску: волна 0 (каркас) → волны 1–3 (домены) → волна 4 (сборка).

    0. Как пользоваться

    • Лиду (сборщику): §1–§3 задают правила и контракты; §4 — каркас, который делается первым; §15 — сборка, §16 — волны, §17–§18 — шаблоны задания и отчёта.
    • Агенту домена: прочитать §1–§3 (правила и контракты), затем свою секцию из §4–§14 целиком. Ничего вне своей секции и вне списка «Файлы» трогать нельзя.
    • Всё, что не описано явно (структура ответа устройства, коды ошибок), берётся из mcp-server.md §2 и из кода прошивки, а не додумывается.

    Главное правило: пакет считается выполненным, когда он компилируется, проходит свои тесты и не изменил ни одного чужого файла. «Работает у меня в голове» не считается.

    1. Принципы нарезки

    1. Один пакет = один домен API. Домен = группа REST-эндпоинтов с общим смыслом (команды, настройки, датчики, журналы…). Домены почти не пересекаются, поэтому их можно делать параллельно.
    2. Каркас — блокер. Всё, что нужно всем (транспорт, конфиг, клиент устройства, ошибки, схемы телеметрии, тестовый двойник), делает WP0. До его приёмки домены не начинаются.
    3. Владение файлами жёсткое. У каждого файла ровно один владелец. Пересечение = конфликт при параллельной работе, поэтому оно запрещено, даже если «одна строчка».
    4. Контракт важнее реализации. Агент домена может поменять внутренности своего сервиса, но не сигнатуры из §2. Если сигнатуры не хватает — это «запрос на изменение контракта» в отчёте, а не правка чужого файла.
    5. Тесты — часть пакета. Каждый пакет приносит тесты на свои инструменты; приёмка — зелёный npm test на собранном дереве, а не только «код написан».
    6. Сборка — отдельный пакет. Никто из доменных агентов не регистрирует свои инструменты в общем реестре: это делает WP11 одним движением, чтобы не было гонки за src/tools/index.ts.

    // src/errors.ts — WP0
export type ErrorCode =
  | 'device_unreachable' | 'device_timeout' | 'auth_failed' | 'auth_required'
  | 'forbidden_admin_required' | 'feature_unsupported' | 'queue_full' | 'guard_blocked'
  | 'validation_failed' | 'partial_apply' | 'busy' | 'not_found'
  | 'confirmation_required' | 'disabled_by_policy' | 'unsupported_operation'
  | 'device_error' | 'internal_error';

export interface ErrorEnvelope {
  ok: false;
  error: {
    code: ErrorCode;
    message: string;   // по-русски, для человека
    hint?: string;     // по-русски, что сделать
    retryable: boolean;
    details?: Record<string, unknown>;
  };
}

export class OcError extends Error {
  constructor(code: ErrorCode, message: string, opts?: {
    hint?: string; retryable?: boolean; details?: Record<string, unknown>;
    httpStatus?: number; cause?: unknown;
  });
}

export function fail(code: ErrorCode, message: string, opts?: {
  hint?: string; retryable?: boolean; details?: Record<string, unknown>;
}): ErrorEnvelope;

export function errorEnvelope(error: unknown): ErrorEnvelope;

    Правила:

    • сообщения и hint — по-русски; code, ключи details — латиницей;
    • OcError бросаем внутри домена, конверт fail возвращаем из обработчика инструмента;
    • неизвестные исключения не глотаем: их поймает registerTools и превратит в internal_error.

    2.3 Правило про outputSchema и structuredContent

    SDK проверяет structuredContent на соответствие outputSchema, если схема объявлена, и ведёт себя строго к лишним полям. Поэтому:

    • по умолчанию outputSchema не указываем, а structuredContent отдаём (SDK это разрешает);
    • если конкретному инструменту нужна строгая схема вывода — сначала подтвердить поведение тестом (WP0 обязан это проверить и зафиксировать в test/registry.test.ts);
    • поля ответа описываем в description инструмента и в типах TypeScript.

    WP0 обязан проверить оба сценария (со схемой и без) и записать вывод в README пакета — от этого зависит весь каталог.

export interface RequestOptions {
  query?: Record<string, string | number | boolean | undefined>;
  timeoutMs?: number;
  anonymous?: boolean;                 // без Authorization (signIn)
  rawBody?: string;                    // CSV/текст как есть
  headers?: Record<string, string>;
}
export interface HttpResponse {
  status: number;
  headers: Record<string, string>;
  body: string;                        // всегда строка
  ms: number;
}
export interface CommandAccepted {
  accepted: true;
  command: string;
  warnings: string[];
  raw: string;
}

export class DeviceClient {
  get<T>(path: string, schema: z.ZodType<T>, opts?: RequestOptions): Promise<T>;
  post<T>(path: string, body: unknown, schema: z.ZodType<T>, opts?: RequestOptions): Promise<T>;
  put<T>(path: string, body: unknown, schema: z.ZodType<T>, opts?: RequestOptions): Promise<T>;
  del<T>(path: string, body: unknown, schema: z.ZodType<T>, opts?: RequestOptions): Promise<T>;

  /** POST /rest/commands с разбором 200/409/503. */
  sendCommand(name: string, parameters?: string): Promise<CommandAccepted>;

  /** Один писатель на устройство: записи выполняются строго последовательно. */
  withWrite<T>(key: string, fn: () => Promise<T>): Promise<T>;

  /** Сырой запрос — только для CSV, 202-поллинга и нестандартных случаев. */
  request(method: string, path: string, body?: unknown, opts?: RequestOptions): Promise<HttpResponse>;
}

    Гарантии, на которые могут рассчитывать домены:

    Гарантия Поведение
    Авторизация signIn, кэш JWT, один повтор после 401; 404 на verifyAuthorization = security off
    Ретраи только GET (сеть, 502-504, 503 queue_full), экспоненциальный backoff, 3 попытки
    Запись POST/PUT/DELETE не ретраятся; сериализуются через withWrite при необходимости
    Ошибки 401/403/404/503 → соответствующие OcError; тело сохраняется в details.body
    Сырой лог каждый обмен пишется в RawLogger согласно SSVC_RAW_LOG
    Валидация ответ парсится zod-схемой домена; несоответствие → OcError('device_error')

    6. WP2 — команды, ожидание, предохранители

    Обновление после §9 (обязательно к исполнению). Успешный POST /rest/commands теперь отдаёт JSON: {"status":"accepted","command":"<имя>","commandId":<число>,"warnings":[…]?}. Каждая команда журналируется, и GET /rest/commands/{id} возвращает {id,command,state,queued_at,started_at,finished_at,ok,reason,confidence:"transport"}, где state ∈ queued/running/sent/done/rejected/timeout. Поэтому: - accepted в инструменте должен содержать command_id и warnings[] (предупреждения ≠ отказ); - для команд, которые ждут реакции (status, version, get_settings, set, get_log), инструмент опрашивает GET /rest/commands/{id} до терминального состояния и возвращает его; - для start/next/pause/resume/stop терминальное sent означает «ушло в UART, ответа не будет» — это норма, а не ошибка; фактический результат берётся из oc_wait_for_change/снимка; - 404 на /rest/commands/{id} — «запись вытеснена» (журнал 16 записей, TTL 10 мин), а не «команда не выполнялась»: в этом случае падать нельзя, нужно вернуть command_id + state:"unknown"; - confidence:"transport" всегда, и это надо писать в описании инструмента прямо: подтверждение транспортное, физического действия сервер не подтверждает. Коды 409/503/501 из таблицы ниже остаются в силе.
