    REST-контракт OpenConnect: заметки разведки по исходному коду

    Рабочий справочник для разработчиков MCP-сервера и мок-устройства. Снят с кода, а не с RFC. Каждое утверждение сопровождается ссылкой файл:строка; всё, что не удалось подтвердить чтением кода, помечено «не подтверждено» и вынесено в § N.

    Два следствия, которые надо держать в голове постоянно:

    1. Все HttpEndpoint<T>-сервисы регистрируют только GET и POST — PUT/PATCH/DELETE для них не существуют (lib/framework/HttpEndpoint.h:62-114). Метод, которого нет, даёт не 405, а 404 text/plain «Not Found» из catch-all (WebHandlers.cpp:313 в .pio/libdeps/.../ESPAsyncWebServer/src).
    2. Провал любого предиката (IS_ADMIN в том числе) отдаётся как 401 без тела, не 403 (lib/framework/SecuritySettingsService.cpp:129-155).

    A. Таблица маршрутов

    Предикат — то, что реально передано в wrapRequest/wrapCallback или отсутствует вовсе. В сборке FT_SECURITY=0 все предикаты игнорируются: wrapRequest/wrapCallback возвращают обработчик как есть, authenticateRequest всегда отдаёт admin-пользователя (SecuritySettingsService.cpp:191-214), а /rest/signIn и /rest/verifyAuthorization не регистрируются (весь AuthenticationService.cpp под #if FT_ENABLED(FT_SECURITY), строка 18) → на не-secure сборке это 404.

    E. Аутентификация

    E.1 /rest/signIn

    POST /rest/signIn — {"username":"…","password":"…"} (AuthenticationService.cpp:27-43). Успех: 200 {"access_token":"<JWT>"}. Провал: 401 без тела (:42). Тело не объект → тоже 401 (проверка json.is<JsonObject>(), :29). Пустые поля не валидируются отдельно — просто не совпадут с пользователем.

    E.2 JWT

    • Payload ровно {"username":…,"admin":bool} (SecuritySettingsService.cpp:98-102).
    • Подпись HMAC-SHA256 по секрету (ArduinoJsonJWT.cpp:38-52), заголовок JWT_HEADER (:62).
    • exp/iat/nbf не добавляются (ArduinoJsonJWT.cpp:54-68), но при проверке payload сравнивается на полное равенство с {"username","admin"} (SecuritySettingsService.cpp:104-110): токен с любыми дополнительными полями будет отвергнут. MCP-сервер не должен «обогащать» токен.
    • Секрет: FACTORY_JWT_SECRET → securitySettings.jwtSecret (SecuritySettingsService.cpp:22,62-65); смена секрета инвалидирует все токены.
    • Передача: Authorization: Bearer <jwt> (:43-53) либо ?access_token=<jwt> (:54-58).
    • GET /rest/generateToken?username=<u> — только admin, 200 {"token":"<jwt>"} или 400/401 (SecuritySettingsService.cpp:157-178).

    G. Расхождения с RFC

    Формат: «в RFC сказано X → в коде Y». Проверялись docs/develop/mcp-server.md §2/§2.5/§4 и docs/develop/mcp-server-agents.md §5–§13.

    1. 403 против 401. RFC §2.2 и WP4/WP8 предписывают маппить отказ admin-доступа с 403 в forbidden_admin_required (mcp-server.md:114, mcp-server-agents.md:596). В коде все предикаты, включая IS_ADMIN, отвечают 401 без тела: SecuritySettingsService.cpp:136,150. Единственный 403 в прикладном коде — зарезервированный бит реле (OpenConnectHandler.cpp:294), и WP5 сам это признаёт (mcp-server-agents.md:686-687). Следствие: 401 в MCP-сервере означает «токен не тот или не хватает прав», различить нельзя без повторного логина под admin.
    2. /rest/features без аутентификации. RFC §2.4.1 помечает его как auth (mcp-server.md:136). В коде маршрут регистрируется голой лямбдой без wrapRequest (FeaturesService.cpp:23-29) — доступен без токена, и именно так его читает UI до логина (interface/src/routes/+layout.ts:8). Это единственный способ узнать security:false без 401.
    3. admin у фреймворковых маршрутов преувеличен. RFC §2.4.1: systemStatus, coreDump, wifiStatus/wifiSettings/..., apStatus, ntpStatus, mqttStatus — «admin» (mcp-server.md:137-142). В коде systemStatus, coreDump, все *Status — IS_AUTHENTICATED (SystemStatus.cpp:126, CoreDump.cpp:34, WiFiStatus.cpp:27, APStatus.cpp:29, NTPStatus.cpp:26, MqttStatus.cpp:29); admin нужен только для *Settings, scanNetworks, listNetworks, time, restart, factoryReset, uploadFirmware, downloadUpdate, generateToken (WiFiScanner.cpp:25-35, NTPSettingsService.cpp:49-53 и т. д.). Плюс /rest/restart — только POST, «GET/POST» в RFC неверно (RestartService.cpp:24).
    4. type датчика в /rest/sensor. RFC WP1 приводит "type": "DS18B20" (mcp-server-agents.md:411, повторено в :588). В коде type — это класс измеряемой величины: thermal / pressure / level (DS18B20Sensor.cpp:91-92, BMP581Sensor.cpp:252-253, Xkc25Sensor.cpp:312-313); модель датчика в ответе вообще не передаётся. Единица BMP581 — "мм рт. ст.", а не °C (BMP581Sensor.cpp:248-249).
    5. status процесса не имеет значений stopped/error. RFC и каталог инструментов рассчитывают на «процесс остановлен/ошибка» (mcp-server-agents.md:425, mcp-server.md:613). В коде ProcessState::STOPPED и PROCESS_ERROR не имеют case в stateToString (RectificationProcess.cpp:163-181) → отдаётся строка "unknown". То же со стадией SETTINGS: в stageToString её нет (:117-139), хотя metadata.rectificationStages рекламирует settings (OpenConnectHandler.cpp:232-235). Zod-схема обязана включать unknown, а MCP не должен трактовать unknown как «процесс не идёт».
    6. GET /rest/logs из idle не возвращает "status":"list". RFC WP7 показывает GET /rest/logs → {status:"list", files:[…]} как ответ на первый запрос (mcp-server-agents.md:755-756). В коде запрос из idle сначала резервирует сессию и ставит команду (HandlerRegistrator.cpp:387-410), а снимок берётся сразу после, когда статус — QUEUED_LIST, что отображается как receiving (SsvcLogProtocol.h:484, HandlerRegistrator.cpp:319-335). То есть первый ответ — {"status":"receiving","total":0, "received":0}, и список приходит только следующим опросом. Кроме того, в RFC не перечислены 409 api_version_unsupported (с required_api/device_api) и 400 invalid_process_id (HandlerRegistrator.cpp:360-363,441).
    7. Индекс датчика XKC-25. WP6: «index 0..3» (mcp-server-agents.md:723). В коде максимум три слота: kMaxXkc25Sensors = 3 (OpenConnectHardwareConfig.h:146) и проверка index >= kMaxXkc25Sensors → 400 {"error":"index out of range"} (OpenConnectHandler.cpp:652-655), то есть допустимо 0..2. Таймаут — поле timeoutMs, а не timeout_ms, и он зажимается сверху 5000 мс, а не «1000..15000» (OpenConnectHandler.cpp:485-487,678-680).
    8. supported:false не единственная форма отказа реле. RFC §2.5 п.9 и WP5 утверждают, что GPIO-сборка отдаёт {"supported":false} вместо ошибки (mcp-server.md:223, mcp-server-agents.md:683-684). Для GET это верно (OpenConnectHandler.cpp:140,154,252), но POST /rest/oc/relay/override на GPIO-сборке отдаёт 400 {"error":"PCF8574 relay path not enabled in this build"} (:269-271). Обработчик должен считать признаком GPIO-сборки и этот 400.
    9. Ключи /rest/systemStatus. WP9 приводит {heap, uptime, firmware} (mcp-server-agents.md:875). Реальные ключи: free_heap, total_heap, used_heap, min_free_heap, max_alloc_heap, uptime, firmware_version, esp_platform, cpu_type, psram_size/free_psram (при наличии PSRAM) и др. (SystemStatus.cpp:136-163) — ключей heap и firmware не существует.
    10. Поля только для чтения в /rest/settings. RFC WP3 перечисляет закрытый набор PARAM_HANDLERS верно (mcp-server-agents.md:541-545), но не предупреждает, что GET отдаёт ещё ~17 ключей, которых нет в обработчиках: sound, pressure, relay_inverted, relay_autostart, autoresume, auto_mode, hearts_temp_shift, hearts_pause, tp2_shift, tp_filter, signal_tp1_control, signal_inverted, tp1_control_temp, tp1_control_start, stab_limit_time, stab_limit_finish, backlight (SsvcSettings.cpp:114-139 против SettingsSetterHandlers.cpp:20-229). PUT с ними вернёт 200, но в ignored. MCP-инструмент oc_update_settings не должен объявлять их записываемыми, иначе «успех» будет ложным.
    11. Состав /rest/subsystem. RFC §2.4.2 фиксирует шесть имён (mcp-server.md:154). Фактически набор зависит от конфигурации: добавляются lcd1602_display и xkc25_sensor, а atm_sensor присутствует только при pressureSensorEnabled (SsvcOpenConnect.cpp:203-236). Схема ответа должна быть «словарь bool с известными ключами, остальные допустимы».
    12. 200 text/plain у /rest/commands — не всегда. RFC §2.5 п.10 и §2.4.2 говорят «200 = принято, text/plain» (mcp-server.md:153,224). Если предстартовая проверка XKC-25 дала предупреждения, ответ — 200 application/json {"status":"accepted","command":"start","warnings":[…]} (CommandHandler.cpp:96-107). Также в RFC отсутствуют 501 Command not implemented (:40-44) и 400 на кривое тело (:26-34), а отказ feature_unsupported — это 409 text/plain, а не JSON (:82-84).
    13. /rest/sensors/thresholds и /rest/profiles/import. RFC §2.5 п.11 верно говорит, что их нет в прошивке (mcp-server.md:225), но не описывает, что реально происходит при вызове: thresholds → 404 catch-all (маршрута нет вообще), import → перехватывается BackwardCompatible-матчером POST /rest/profiles и отдаёт 400 «Missing or invalid 'name' field» (HandlerRegistrator.cpp:294, ProfileHandler.cpp:74-77). Для мок-устройства это разные ответы, и их стоит воспроизвести.
    14. lastUpdate — не время. RFC WP1 называет поле last_update_ms и говорит о «возрасте снимка» (mcp-server-agents.md:424,438). В коде это millis() (мс с загрузки) (TelemetryService.cpp:157), то есть привязать его к настенному времени нельзя; «возраст» считается только относительно другого lastUpdate с того же устройства.
    15. Семантика xkc25TriggerAction расходится с UI. В прошивке 0 = PAUSE, 1 = ABORT, 2 = NOTIFY (OpenConnectHardwareConfig.h:95-99), а в типах фронтенда написано обратное: «0 — только уведомление, 1 — пауза отбора, 2 — прерывание» (interface/src/lib/types/ssvc.ts:246-251). RFC WP6 приводит "triggerAction": 1 без расшифровки (mcp-server-agents.md:705). На живом устройстве нужно проверить, какая интерпретация соответствует фактическому поведению (§ N).
    16. POST у read-only сервисов. RFC нигде не упоминает, что HttpEndpoint регистрирует POST для всех состояний: POST /rest/telemetry, POST /rest/sensor существуют и отвечают 200 текущим состоянием (HttpEndpoint.h:78-114; TelemetryState::update → UNCHANGED, TelemetryService.h:47-50). Мок-устройство должно их принимать, а MCP — не считать, что «POST /rest/sensor» меняет данные.
    17. Дефолты порогов тревог. RFC приводит {enabled, min:0, dangerous:80, critical:100} (mcp-server-agents.md:592) как форму. Код сериализует дефолты 0/50/80 (AlarmThresholdService.h:54-59), а при разборе подставляет 0/80/100 (:62-69), поэтому частичный POST может «сдвинуть» пороги, которых клиент не передавал. Это надо явно обрабатывать в MCP: всегда отправлять все четыре поля.

    Дополнительно (не про RFC, но про соседнюю документацию): docs/develop/api/sensors.md:20-40 описывает PUT /rest/sensors/zone с JSON-телом {"sensorId","zone"} — это неверно, параметры передаются только в query (§ B.7), а поля называются address и zone.

    H. Ловушки

    Дополнение к RFC §2.5 (mcp-server.md:209-229).

    H.1 Порядок регистрации и матчеры

    1. Строковый маршрут в ESPAsyncWebServer — не exact, а BackwardCompatible: path == value || path.startsWith(value + "/") (WebServer.cpp:216-232,336 в .pio/libdeps/.../ESPAsyncWebServer/src). Матчится первый подходящий обработчик (WebServer.cpp:142-151), поэтому порядок регистрации = приоритет.
    2. GET /rest/files (маршрут 67) зарегистрирован раньше GET /rest/files/* (68) и перекрывает его: любой GET /rest/files/<path> уходит в обработчик дерева. Скачивание файла в этой ревизии недостижимо (см. § N — проверить на живом устройстве).
    3. GET /rest/logs намеренно зарегистрирован через AsyncURIMatcher::exact (HandlerRegistrator.cpp:341-347) — иначе он перекрывал бы /rest/logs/{id}. Это же правило придётся соблюдать в мок-устройстве.
    4. DELETE /rest/files/* и DELETE /rest/logs регистрируются после GET-маршрутов; для DELETE перекрытий нет, потому что canHandle проверяет ещё и метод (WebHandlers.cpp:302-307).
    5. /rest/profiles/* регистрируются до /rest/profiles (HandlerRegistrator.cpp:240-297) — иначе POST /rest/profiles съел бы set-active, copy, save, content.
    6. Завершающий слэш ведёт себя по-разному в зависимости от матчера. У обычного строкового маршрута (/rest/settings) BackwardCompatible пропускает и /rest/settings, и /rest/settings/: второй вариант начинается с value + "/" (WebServer.cpp:216-232). У exact-маршрута /rest/logs (HandlerRegistrator.cpp:347) /rest/logs/ не совпадёт и уйдёт в обработчик /rest/logs/* с пустым id → 400 {"error":"invalid_process_id"} (HandlerRegistrator.cpp:436-443). Вывод: слешей не добавлять; для мок-устройства это два разных поведения, и /rest/logs/ нужно воспроизводить как 400, а не как список.
    7. Тот же эффект у вложенных путей: /rest/oc/xkc25/status/ совпадёт с /rest/oc/xkc25/status, а /rest/sensor/ — с /rest/sensor (оба — HttpEndpoint, строковые пути SensorDataService.h:39, OpenConnectHandler.cpp:187).

    H.2 Вложенность против плоскости

    • GET /rest/settings → вложенный ssvcSettings; PUT → плоский объект. Ошибка в любую сторону тихая: PUT с обёрткой {"ssvcSettings":{…}} уйдёт в ignored, вернёт 200 с "accepted":0 и ничего не применит (SettingsHandler.cpp:64-72,141-148), а разбор GET без разворачивания даст undefined во всех полях.
    • GET /rest/zones, /rest/alarms → вложенные zones/thresholds; POST ждёт ту же обёртку (SensorConfigService.cpp:32, AlarmThresholdService.cpp:69), иначе CHANGED не наступит и ответ будет 200 без изменений.
    • GET /rest/profiles → массив, а не {profiles:[…]}.
    • /rest/oc/info → вложенные ssvc и oc; /rest/telemetry → telemetry, status + lastUpdate в корне.

    H.3 Дефолты и необязательные поля

    • relay/override: enable по умолчанию true, energized — false (OpenConnectHandler.cpp:297-298); передавать оба всегда.
    • xkc25TriggerAction/startGuardMode дефолты: PAUSE и WARN (OpenConnectHardwareConfig.h:85,105).
    • Пороги тревог: см. § G.17.
    • Почти вся телеметрия условна (§ B.1) — «нет поля» ≠ «ноль».
    • late_heads/tails в /rest/settings отсутствуют, если не пришли с устройства (дефолты {-1,-1}, SsvcSettings.h:272-277), а tails_temp — если <= 0 (SsvcSettings.cpp:90-93).

    H.4 Асинхронность и таймауты

    • POST /rest/commands → 200 = «в очереди» (CommandHandler.cpp:74-77); результат команды узнать неоткуда, кроме последующего состояния.
    • PUT /rest/settings → 200 = SET-пакеты поставлены в очередь; фактическое применение — после ответа контроллера, повторный GET /settings сразу может вернуть старое. Ретрай после 503 запрещён — часть SET уже ушла (§ B.5).
    • POST /rest/oc/xkc25/calibrate {"step":"verify_return"} → 202; результат — только через GET /rest/oc/xkc25/verify-status (опрос).
    • GET /rest/logs/{id} → 202 до готовности; готовый результат живёт 5 минут (HandlerRegistrator.cpp:339), после — снова запрос и новая UART-сессия.
    • PUT /rest/subsystem {"telegram_bot":true} может занять десятки секунд; отдельного статуса готовности нет, а GET отдаёт целевой флаг сразу (SubsystemManager.cpp:79-102).
    • GET /rest/telemetry обновляется внутренним таймером раз в 2 с (TelemetryService.cpp:12), GET /rest/sensor — циклом опроса датчиков, поэтому снимки «разъезжаются» по времени.
    • GET /rest/oc/hardware-config и PUT выполняют реальные I²C-пробы под Guard шины (OpenConnectHandler.cpp:367-397,441-471) — на медленной/висящей шине запрос может тянуться.

    H.5 Коды, которых не ждёшь

    • 423 у /rest/telegram/config и /rest/vk/config при выключенной подсистеме (TelegramBotHandler.cpp:27, VkBotHandler.cpp:139).
    • 502 у /rest/vk/peers при ошибке VK API (VkBotHandler.cpp:230).
    • 409 text/plain (не JSON) у /rest/commands при feature_unsupported (CommandHandler.cpp:82-84).
    • 500 text/plain у /rest/commands при исключении (:110-113).
    • 409 у /rest/profiles/copy при «источник не найден» — не 404 (ProfileHandler.cpp:176).
    • 401 без тела у любого admin-маршрута — не путать с «нет такого маршрута» (404 text/plain).
    • Нет метода — 404, а не 405 (см. § A).

    H.6 Прочее

    • ?statusOnly=0 == ?statusOnly=1 (HandlerRegistrator.cpp:373): проверяется наличие параметра.
    • GET /rest/settings может отдавать mode-зависимый набор полей (§ B.5) — сравнивать профили «в лоб» нельзя.
    • PUT /rest/settings не поддерживает sound/pressure/... (§ C.3) — «настройка есть в GET, но не пишется».
    • DELETE с JSON-телом (/rest/profiles/delete) — работает, потому что wrapCallback парсит тело независимо от метода (HandlerRegistrator.cpp:306-309), но многие HTTP-клиенты это ломают: проверять, что тело реально ушло.
    • /rest/profiles/content?id= — id в query; PUT-подобное «обновление содержимого» — это POST /rest/profiles/content.
    • POST /rest/zones удаляет всё, чего нет в теле (§ B.3): «частичное обновление» карты зон невозможно, только полная замена.
    • POST /rest/alarms ведёт себя так же (§ B.4).
    • Адреса датчиков — верхний регистр (SensorManager.cpp:165-171); stringToAddress принимает оба регистра (strtol по hex), но SensorManager хранит и сравнивает ключи в верхнем, поэтому 28ff... в query приведёт к 404 «Sensor not found» (§ N: проверить).
    • GET /rest/oc/info кэшируется UI до переподключения (interface/src/lib/api/ssvcApi.ts:35-79) — для MCP всегда читать заново после старта процесса/смены контроллера.

    J.2 Идентификатор команды и корреляция ответов

    Идентификатора у команды нет. SsvcCommand — это {type, parameters, attempt_count, safetyEpoch, generation}; ни порядкового номера, ни UUID, ни отметки времени (SsvcCommandsQueue.h:283-298 и объявление структуры там же). Узнать «судьбу» конкретной команды через REST нельзя.

    Корреляция есть только косвенная, по эху request. Контроллер в ответе возвращает поле request с текстом команды (SsvcConnector.cpp:417-423), и RX-задача разветвляется по нему: GET_SETTINGS → BIT10 (:435-443), VERSION → BIT11 (:444-448), GET_LOG → трансфер (:423-434), любой другой result == "OK" → BIT9 (:450-454), иначе → BIT1 (:455-457). Воркер ждёт бит, соответствующий типу текущей команды (commandToExpectedBit, SsvcCommandsQueue.h:219-230: BIT9 для STOP/PAUSE/RESUME/NEXT/AT/SET/STATUS/START, BIT10 — GET_SETTINGS, BIT11 — VERSION). Так как воркер один, а биты перед отправкой очищаются (SsvcCommandsQueue.cpp:365-370), корреляция держится на сериализации, а не на номере.

    Ловушки этой схемы:

    • BIT9 взводится любым ответом с result:"OK" — если SSVC пришлёт «чужой» ответ (например, на автоматический GET_SETTINGS из :480), он засчитается текущей команде;
    • кадры type:"response" не попадают в lastMessage (:399 — только не-лог, но BIT9-ветка до записи lastMessage; фактически lastMessage пишется для всех не-лог кадров :399-406, а storeResponse — только для VERSION/OK: :446,452);
    • команды, на которые SSVC может не ответить вовсе (STOP во время лог-сессии, GET_LOG), дают «нет ответа» = таймаут, а не «ошибка» — REST уже вернул 200 «принято».

    J.4 Минимальный дизайн commandId

    Идея: не менять UART-протокол, а добавить журнал попыток в самой очереди.

    Хранение. Кольцевой буфер фиксированного размера в SsvcCommandsQueue (не в куче):

    struct CommandRecord {           // ~96–128 Б
  uint32_t id;                   // монотонный счётчик, выдаётся в enqueue()
  SsvcCommandType type;          // 1 Б
  uint8_t state;                 // queued|running|done|rejected|timeout
  char params[64];               // усечённые параметры (SET/STATUS/GET_LOG)
  uint32_t queuedAt, startedAt, finishedAt;  // millis()
  int8_t rejection;              // индекс строки причины
  bool answeredOk;               // пришёл ли BIT9/BIT10/BIT11, а не BIT1
};
static CommandRecord _journal[16];   // ~2 КБ .bss, heap 0

    Почему 16: воркер один, реальная скорость — единицы команд в секунду, а окно «узнать судьбу» нужно на время одного UI-раунда; 16 записей × 5 минут TTL с запасом покрывают это. Усечение params до 64 Б достаточно для SET одного-двух полей и STATUS (лимит SSVC_SET_CMD_MAX_LEN 300 Б — SsvcUartApiSpec.h, но хранить полный текст в журнале не нужно).

    Переходы. queued — в enqueue() после успешного xQueueSend (:790-808); running — в воркере перед отправкой (:372); done — после успешного bitCallbacks (:500-560); rejected — при rememberRejection (там же, где сейчас пишется причина); timeout — когда attempt_count исчерпан (:556-570).

    API. POST /rest/commands → добавить в 200-ответ "commandId": N (тело уже бывает JSON при warnings — CommandHandler.cpp:96-107; для text/plain-ветки :109 нужен переход на JSON или заголовок X-Command-Id). GET /rest/commands/{id} → {id, command, state, queuedAt, startedAt, finishedAt, ok, reason}; регистрировать exact-матчером рядом с /rest/commands (HandlerRegistrator.cpp:73-78), иначе POST /rest/commands перехватит GET /rest/commands/5 (см. § H.1.1). 404 — если записи нет/истекла.

    Что считать результатом — два варианта:

    A. Транспортный (рекомендую) B. Семантический
    Что отдаём queued/running/done/timeout/rejected + ok = взведён ли бит успеха пытаемся вытащить result/request из последнего ответа
    Плюсы всё уже есть в коде: биты, попытки, отказы; ноль изменений в UART; честно отражает «мы отправили и получили/не получили ответ» ближе к «команда выполнена»
    Минусы done ≠ «применено»: SSVC может ответить OK и не выполнить; для START ответа может не быть вовсе корреляции нет: при двух командах подряд последний ответ нельзя привязать к конкретной; lastResponse перезаписывается (SsvcConnector.cpp:446,452); часть команд молчит
    Риски ложное «done» при чужом OK (§ J.2) требует правки протокола SSVC (номер в команде и в ответе) — вне этой прошивки

    Практический компромисс: вариант A + явное поле confidence:"transport" и текст ошибки reason:"no_response" для таймаута; для START/NEXT/RESUME/STOP не обещать done, а отдавать sent (ответа может не быть — isIdempotentRetry уже кодирует это знание, SsvcCommandsQueue.cpp:62-70). Долгосрочно — добавить в SSVC-протокол эхо-номер (SET #42 ...), и тогда вариант B становится корректным.

    Риски памяти/поведения: журнал статический (2 КБ .bss), но enqueue() вызывается из REST-задачи, воркер — из своей; нужен мьютекс (уже есть _rejectionMutex, лучше отдельный). TTL и перезапись кольца обязательны, иначе GET /rest/commands/{id} будет отдавать «чужую» команду после переполнения. Никаких std::string в записи — только char[64], иначе фрагментация кучи на каждой команде.

    K. Безопасность и JWT

    K.1 Структура и проверка

    • Payload — ровно два поля: {"username": "<строка>", "admin": <bool>} (SecuritySettingsService.cpp:98-102).
    • Подпись — HMAC-SHA256 (ArduinoJsonJWT.cpp:38-52), заголовок фиксированный JWT_HEADER (:62); exp, iat, nbf, iss, aud не добавляются (:54-68).
    • Транспорт: Authorization: Bearer <jwt> (SecuritySettingsService.cpp:43-53) либо ?access_token=<jwt> (:54-58). Cookie-сессии нет — ни Set-Cookie, ни чтения cookie в authenticateRequest (:29-58).
    • Refresh-эндпоинта нет: единственные источники токена — POST /rest/signIn (AuthenticationService.cpp:27-44) и GET /rest/generateToken?username= под admin (SecuritySettingsService.cpp:157-178); оба идут через один generateJWT (:112-118).

    K.2 Что именно ломается при добавлении exp/iat

    validatePayload сравнивает разобранный payload с эталоном, собранным из БД, и требует полного равенства объектов (SecuritySettingsService.cpp:104-110). Любое дополнительное поле в токене делает объекты неравными ⇒ authenticateJWT возвращает «невалиден» ⇒ 401 на всех маршрутах, включая /rest/verifyAuthorization. То есть:

    • добавили exp при выдаче → сломались все клиенты, включая веб-UI (он хранит токен и шлёт его как есть);
    • добавили проверку exp без изменения выдачи → старые токены (без exp) должны считаться валидными, иначе после обновления прошивки все разлогинены;
    • generateToken и signIn используют один билдер, поэтому «половинчатая» правка невозможна: либо оба пути добавляют exp, либо ни один.

    K.3 Совместимый путь

    Заменить сравнение объектов на сравнение по подмножеству:

    bool valid = payload["username"].is<const char*>() &&
             payload["admin"].is<bool>() &&
             strcmp(payload["username"], user.username) == 0 &&
             payload["admin"].as<bool>() == user.admin &&
             (!payload["exp"].is<long>() || payload["exp"].as<long>() > time(nullptr)) &&
             (!payload["nbf"].is<long>() || payload["nbf"].as<long>() <= time(nullptr));

    Плюсы: старые токены без exp продолжают работать (условие «если есть — проверить»); новые получают срок жизни; подпись по-прежнему защищает от подделки. Минусы/риски:

    • нет отзыва: выданный токен живёт до exp, сменить пароль/секрет — единственный способ инвалидировать (сейчас так же, но бессрочно);
    • часы: exp требует синхронного времени; time(nullptr) до NTP-синхронизации = эпоха 1970 ⇒ все токены «просрочены» сразу после загрузки. Нужно либо не проверять exp, пока время < порога (например, time(nullptr) < 1700000000), либо выдавать токен с exp только после синхронизации;
    • тест на живом устройстве обязателен: токен, выданный до обновления, должен приниматься после (обратная совместимость), а токен с exp в прошлом — отвергаться.

    Правка локализована в одной функции (validatePayload) + один билдер (populateJWTPayload/ generateJWT), но затрагивает вход во всё устройство, поэтому её надо катить вместе с FEATURES/UI-логикой «перелогиниться при 401».

    L. Транспорт, TLS, CORS

    L.1 TLS на сервере: чего нет

    • Единственный сервер создаётся как AsyncWebServer server(80) (src/main.cpp:16) и передаётся в ESP32SvelteKit (:18); mDNS объявляет http и ws на порту 80 (ESP32SvelteKit.cpp:133-134). HTTP-only.
    • В используемой версии ESPAsyncWebServer нет класса AsyncWebServerSecure: в src/ только WebServer.cpp, WebHandlers.cpp и т. д. (ls .pio/libdeps/.../ESPAsyncWebServer/src), а beginSecure(cert, key, password) объявлен под #if ASYNC_TCP_SSL_ENABLED (ESPAsyncWebServer.h:1703-1706) — этот макрос нигде не определён (проверено grep’ом по ESPAsyncWebServer/src и AsyncTCP/src), то есть для ESP32-S3 метод недоступен.
    • ssl_certs/ — это исходящие CA-бандлы для OTA (ssl_certs/cacert.pem ≈ 68 КБ, DigiCert_Global_Root_CA.pem), вшитые через board_build.embed_files; серверного сертификата/ключа в репозитории нет.

    Вывод: «опциональный HTTPS» — это не флаг, а замена транспорта. Минимум:

    1. серверный сертификат X.509 + ключ (RSA-2048 или EC P-256; для ESP32-S3 предпочтительнее EC — меньше RAM на рукопожатие), с SAN на openconnect.local/IP;
    2. esp_https_server (esp-tls/esp_http_server) или форк ESPAsyncWebServer с TLS; при этом ESP32SvelteKit завязан на AsyncWebServer* (ESP32SvelteKit.h:220,116-119) и на AsyncWebSocket для /ws/events (EventSocket.h:43), а WebSocket-поверх-TLS в этой связке отсутствует — понадобится отдельный WS-стек для wss://;
    3. правки: тип сервера в ESP32SvelteKit/SsvcOpenConnect::begin (src/main.cpp:44-49 — там server и getSocket()), порт/mDNS (ESP32SvelteKit.cpp:133-134), UI-база URL (interface/src/lib/api/... — сейчас относительные пути), плюс редирект 80→443 или параллельный HTTP для локальной сети.

    Оценки памяти (RSA/ECDSA, mbedtls): рукопожатие ≈ 16–30 КБ heap на соединение, буферы записей ≈ 4–16 КБ — не подтверждено замером; на S3 с PSRAM обычно приемлемо, но при 2–3 одновременных TLS-сессиях + JSON-телеметрия риск OOM реален. Размер образа растёт на ~30–60 КБ (mbedtls уже линкуется для OTA-клиента, поэтому прирост меньше, чем кажется). Проверять free_heap до/после.

    Альтернатива без TLS на устройстве: оставить HTTP в локальной сети, а шифрование возложить на MCP-сервер/реверс-прокси (nginx/caddy) — тогда прошивку трогать не нужно вообще. Это же снимает проблему wss.

    L.2 CORS: как включается и что реально делает

    ENABLE_CORS в platformio.ini:36 закомментирован ⇒ CORS-заголовков нет. При включении:

    • глобально добавляются Access-Control-Allow-Origin: CORS_ORIGIN (по умолчанию "*", ESP32SvelteKit.h:55-56), Access-Control-Allow-Headers: Accept, Content-Type, Authorization, Access-Control-Allow-Credentials: true (ESP32SvelteKit.cpp:123-128);
    • OPTIONS-обработчики регистрируются только у HttpEndpoint<T>-сервисов (HttpEndpoint.h:51-62) и у SleepService (SleepService.cpp:31-40).

    Чего не хватает для рабочего preflight:

    1. Access-Control-Allow-Methods не выставляется нигде — браузер отклонит preflight для PUT/POST/DELETE;
    2. OPTIONS нет у прикладных маршрутов (/rest/settings, /rest/commands, /rest/oc/*, /rest/profiles* — HandlerRegistrator.cpp:56-309), они попадут в catch-all 404 (WebHandlers.cpp:313);
    3. комбинация Allow-Origin: "*" + Allow-Credentials: true запрещена спецификацией — браузер такой ответ отклонит; нужен конкретный origin из конфига;
    4. EventSocket (/ws/events) Origin не проверяет вообще — токен в query решает доступ, но CSRF-подобный сценарий «страница открыла WS с украденным токеном» не блокируется.

    Для MCP-сервера это значит: не рассчитывать на CORS в текущей прошивке; либо включить ENABLE_CORS и добавить Allow-Methods + OPTIONS для прикладных путей (небольшая правка HandlerRegistrator/HttpEndpoint), либо проксировать запросы через сам MCP-сервер (он server-side, CORS не нужен).
