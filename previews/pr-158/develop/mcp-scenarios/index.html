    Пользовательские сценарии MCP-сервера OpenConnect

    Что это. Каталог жизненных сценариев, для которых создаётся MCP-сервер: что делает пользователь, что делает сервер, какой получается эффект. Документ отвечает на вопрос «зачем это нужно человеку», а не «как это устроено внутри».

    Связанные документы: архитектура и план — mcp-server.md; пакеты работ для агентов — mcp-server-agents.md.

    Источники, на которых построены сценарии: - UART API SSVC0059_V2 (SmartModule) — команды, SET, состав телеметрии, события; - руководства пользователя прошивок 2.2.55 (Pro) и 2.3.28 (Pro.3H) — алгоритмы этапов, ограничения параметров, формат журнала; - калькулятор ректификации и редактор профилей OpenConnect — физика процесса, расчёт фракций, производные настройки SSVC.

    0. Как читать каталог

    Каждый сценарий — это паспорт:

    Поле Смысл
    Кто / когда роль пользователя и момент, в который сценарий возникает
    Ситуация живое описание проблемы, ради которой всё затевается
    Ход последовательность действий сервера (инструменты oc_*)
    Эффект что пользователь получает: время, качество, безопасность, деньги
    Требования ветка прошивки, версия API, настройки, без которых сценарий не работает
    Если что-то не так типовые отказы и что сервер сообщает
    Ограничения чего сценарий не гарантирует — чтобы не было ложных ожиданий

    Обозначения приоритета: P0 — первый работающий вариант (чтение и команды), P1 — настройки, P2 — датчики/реле/калибровка, P3 — журналы, профили, анализ.

    Чего в этом документе нет. Здесь не проверялись все сценарии на живом оборудовании — это каталог замысла и приёмки. Проверка каждого сценария выполняется по мере готовности соответствующего пакета работ (см. §10).

    1. Роли

    Роль Кто это Что для него важно
    Домашний ректификатор делает спирт для себя, 1–2 перегона в месяц, колонна в гараже не сидеть у колонны, не испортить продукт, понять, что пошло не так
    Опытный оператор ведёт процесс регулярно, подбирает режимы, ведёт статистику тонкая настройка, воспроизводимость, разбор журналов
    Техподдержка продукта сопровождает чужие установки дистанционная диагностика без выезда
    Разработчик делает прошивку/интерфейс быстрый доступ к состоянию и логам без ручных curl

    Дальше в сценариях роли указаны коротко: домашний, оператор, поддержка, разработчик.

    1.1 Типовой день домашнего пользователя

    Вечером залил сырец, поставил отбор с отсрочкой, ушёл. Ночью колонна работает. Утром нужно понять: прошло ли всё штатно, сколько отобрано, не было ли аварийных остановок. Днём — перегнать хвосты или законсервировать. Сервер нужен в трёх точках: поставить (правильно), присмотреть (не сидя рядом), разобрать (что было).

    2. Опора: что происходит в процессе

    2.1 Две ветки прошивки — два набора этапов

    2.2.55 (Pro) 2.3.28 (Pro.3H)
    Клапан 1 ГУО — головы ГУО — головы
    Клапан 2 УО — тело УО — тело
    Клапан 3 СУО — сивушный узел (хвосты) УОП — подголовники
    Этапы Головы → Тело → Хвосты Головы → Подголовники → Тело
    Параллельный отбор СУО по 4 диапазонам ТД2 (parallel_v3) и ГУО (parallel_v1) УОП фиксированной скоростью (parallel)
    Сброс и снижение голов нет есть (extended_heads, release_*, heads_final)
    Конец процесса tails_finished hearts_finished

    Это первое, что должен понимать сервер: один и тот же запрос означает разное в зависимости от ветки. Отсюда — обязательная проверка GET /rest/oc/info перед сценариями, где это важно.

    2.2 Что видно в телеметрии

    Поле type переключается по этапам: waiting (дежурный), settings (экраны настроек), tp1_waiting (ждём прогрева ТД1), delayed_start (отсчёт), heads, late_heads, hearts, tails.

    Полезные для сценариев поля:

    • common.cfg_chgd — настройки меняли кнопками на контроллере; нужно перечитать GET_SETTINGS;
    • common.tts — сколько секунд до сохранения настроек в энергонезависимую память: если он есть, питание выключать нельзя;
    • common.mmhg, tp1, tp2 — сырые показания; tp1_sap, tp2_sap — приведённые к 760 мм рт. ст. (именно они участвуют в алгоритме, и они отличаются от tp1);
    • tp1_target — зафиксированная температура отбора тела; hysteresis, decrement — действующие;
    • stop, stops, preempt_cnt — была ли остановка отбора, сколько всего, сколько упреждений;
    • alc — расчётная спиртуозность кипящей смеси в кубе;
    • v1, v2, v3 — накопленное время открытия клапанов, секунды;
    • event — heads_finished, late_heads_finished, hearts_finished, tails_finished, ds_error, ds_error_stop, stabilization_limit, manually_closed, manually_opened.

    2.3 Три ловушки, из которых выросли сценарии

    1. PAUSE — это не «пауза процесса». По API PAUSE = вход в ручное управление клапаном текущего этапа (клапан закрыт), RESUME = выход из этого режима. Пользователь, который просит «поставь на паузу», и API, который делает «ручное управление», — разные вещи. Сервер обязан назвать это честно.
    2. START работает только из дежурного режима. Если процесс уже идёт, команда не перезапускает его. Молчание в ответ — не повод повторять.
    3. SET ограничен 300 символами. Полный набор настроек в одну строку не влезает — сервер режет на пакеты и сообщает, что попало в какой.

    3. Сценарии: перед запуском

    A1. «Готов ли контроллер к запуску?»

    Кто / когда — домашний, вечером, за десять минут до старта.

    Ситуация. Сырец залит, колонна собрана, но перед запуском хочется убедиться, что ничего не отвалилось за месяц: датчики на месте, шина I²C жива, датчики уровня не в блокирующем состоянии, UART до SSVC есть.

    Ход. 1. oc_get_info — версия прошивки, API, совместимость. 2. oc_get_hardware_faults — активные сбои и список ответивших адресов I²C. 3. oc_get_sensors — есть ли показания по зонам, нет ли пропавших датчиков. 4. oc_get_xkc25_status — block_start, block_reasons, калибровка. 5. oc_get_process_status — uart_error, стадия waiting.

    Эффект. Один короткий отчёт вместо пяти вкладок веб-интерфейса. Пользователь видит «всё готово» или конкретную причину, по которой лучше не начинать: например, «датчик уровня не калиброван, старт будет заблокирован».

    Требования. Любая ветка, API ≥ 1.7; учётная запись admin (датчики и пороги — только admin).

    Если что-то не так. forbidden_admin_required — сервер прямо говорит, что нужен admin, а не «устройство не поддерживает». device_unreachable — контроллер не отвечает.

    Ограничения. Не проверяет физику: наличие воды в дефлегматоре, плотность набивки, герметичность.

    A2. «Запуск не сработал — почему?»

    Кто / когда — домашний, нажал «Старт» в интерфейсе/у агента, ничего не происходит.

    Ситуация. Команда ушла, но процесс не начался. Причины бывают четыре, и они лечат по-разному: предохранитель датчиков уровня, потеря UART, ожидание прогрева ТД1, отложенный пуск.

    Ход. 1. oc_start → если 409 с block_reasons, это предохранитель XKC-25: разбираем и предлагаем калибровку. 2. Если 200, но стадия не «головы» — oc_get_process_status и oc_get_telemetry: - uartConnectionError: true → связь с SSVC потеряна, команда не дошла; - type: tp1_waiting → контроллер ждёт прогрева колонны (это нормально, не ошибка); - type: delayed_start с countdown → работает отсрочка, всё идёт по плану; - type: waiting при уже отправленном START → процесс не стартовал (START работает только из дежурного режима, либо команда не принята очередью). 3. oc_wait_for_change на ожидаемую стадию с таймаутом — чтобы не гадать «долго ли ещё».

    Эффект. Вместо «не работает» пользователь получает диагноз и следующее действие. Это самый частый вопрос поддержки, и он закрывается за один вызов.

    Требования. API ≥ 1.7. Для разбора block_reasons — P2 (датчики уровня).

    Если что-то не так. queue_full — очередь команд забита, повтор через несколько секунд; feature_unsupported — команда не поддерживается прошивкой, повторять бессмысленно.

    Ограничения. Сервер не «продавливает» запуск: если предохранитель блокирует, он не обходит его.

    A3. «Что вообще умеет мой контроллер?»

    Кто / когда — оператор или поддержка, после обновления прошивки SSVC или OpenConnect.

    Ситуация. В инструкции написано про «Формулу авто 92+» и «Сброс и снижение», а у человека более ранняя прошивка. Или наоборот: он купил свежий контроллер и не знает, что теперь доступно.

    Ход. 1. oc_get_info — api, api_code, api_compatibility, is_support_release. 2. oc_get_capabilities — реестр api_features (predec, extended_heads, formula_auto92, tank_mmhg_act, hearts_preempt_cnt, get_log) с available. 3. Сервер объясняет разницу словами: что заработает, а что нет.

    Эффект. Человек не тратит вечер на настройку функции, которой на его прошивке нет. Поддержка не выясняет это перепиской.

    Требования. API ≥ 1.7.

    Ограничения. api_features описывает UART API, а не маркетинговые возможности прошивки: наличие extended_heads в реестре означает «параметры принимаются», а не «опция включена».

    4. Сценарии: ведение процесса

    B1. «Поставить с вечера и пойти спать»

    Кто / когда — домашний, вечер, процесс на 6–10 часов.

    Ситуация. Нужно: применить профиль, поставить отсрочку, дождаться стабилизации, отобрать головы, перейти к телу. Человек не хочет сидеть рядом, но хочет знать, что старт состоялся.

    Ход. 1. oc_profile_get + oc_get_settings — показать, что именно изменится в контроллере. 2. oc_profile_apply (с подтверждением) — применить настройки профиля. 3. oc_update_settings — точечно поправить то, что зависит от сегодняшнего сырца (например, heads_timer, start_delay, hearts_finish_temp). 4. oc_start (confirm: true) — старт. 5. oc_wait_for_change — последовательно: tp1_waiting → delayed_start → heads с общим бюджетом времени; на каждом шаге короткий отчёт. 6. По достижении heads — сообщить «процесс идёт, головы, ориентировочно до HH:MM» (оценка по countdown).

    Эффект. Пользователь уходит спать, будучи уверенным, что старт произошёл и головы идут. Без сервера он проверяет это вручную через приложение и всё равно сомневается.

    Требования. API ≥ 1.7; auto_mode (автопереходы) включён на контроллере — иначе этапы придётся переключать вручную (см. B2).

    Если что-то не так. guard_blocked — старт не состоялся, данные в block_reasons; partial_apply при настройках — часть SET не принята, процесс не запускается автоматически.

    Ограничения. Оценка времени по countdown — это то, что показывает контроллер; она не учитывает остановки отбора по температуре, поэтому реальное время обычно больше.

    B2. «Этапы переключаются вручную»

    Кто / когда — оператор, у которого auto_mode = 0 (переходы «вручную»).

    Ситуация. Контроллер по завершении голов подаёт сигнал и ждёт. Нужно, чтобы кто-то (или что-то) сказал «дальше» — но без доступа к кнопкам.

    Ход. 1. oc_wait_for_change на событие завершения этапа (heads_finished в event, либо смена type). 2. Сообщение пользователю: «головы отобраны, отбор остановлен контроллером, жду команды». 3. По решению — oc_next (confirm: true), затем oc_wait_for_change на следующий type. 4. Для ветки 2.3 то же самое между late_heads и hearts.

    Эффект. Ручной режим перестаёт требовать физического присутствия: человек подтверждает шаг из любого места, а не стоит у колонны.

    Требования. API ≥ 1.7; auto_mode = 0; для ветки 2.3 — late_heads в поддерживаемых этапах.

    Ограничения. next не «перезапускает» этап и не отменяет его — это аналог кнопки «Далее».

    B3. «Закрыть клапан на время, не останавливая процесс»

    Кто / когда — оператор, заметил, что приёмная ёмкость почти полна, или нужно срочно отлучиться.

    Ситуация. Нужно прекратить отбор, но не останавливать процесс: колонна продолжает работать «на себя», температура стабилизируется.

    Ход. 1. Сервер объясняет до действия: PAUSE — это вход в ручное управление клапаном текущего этапа с закрытым клапаном; RESUME — выход, процесс продолжается с теми же настройками. 2. oc_pause (confirm: true) → oc_get_process_status подтверждает, что стадия прежняя. 3. По готовности — oc_resume (confirm: true).

    Эффект. Человек получает именно то, что просил, и не пугается, что «процесс остановился». Отдельный плюс: в логе событий появятся manually_closed / manually_opened, и это потом видно в разборе.

    Требования. API ≥ 1.7.

    Если что-то не так. oc_pause вне этапа отбора (в waiting/delayed_start) не имеет смысла — сервер предупреждает, а не отправляет команду вслепую.

    Ограничения. Это не «пауза стабилизации» и не отмена декремента: скорость отбора после RESUME остаётся той, что была.

    B4. «Аварийная остановка»

    Кто / когда — любой, при запахе, шуме, переполнении, скачке температуры.

    Ситуация. Нужно остановить отбор немедленно, не дожидаясь, пока очередь команд разберётся с накопленным.

    Ход. 1. oc_emergency_stop — без подтверждения (защитное действие), приоритетная очередь контроллера. 2. oc_get_process_status — подтвердить, что стадия сменилась. 3. Если связи нет — сервер честно говорит device_unreachable и предлагает физические действия (кнопка на контроллере, питание ТЭНа), а не изображает успех.

    Эффект. Единственная команда, которая не требует подтверждения, — та, которая спасает.

    Требования. API ≥ 1.7; emergency_stop поддерживается прошивкой OpenConnect (передаётся как приоритетная команда).

    Ограничения. Останавливает отбор, а не нагрев. Питание ТЭНа и воду сервер не контролирует.

    5. Сценарии: ночной дозор

    C1. «Следить за событиями и звонить, если что»

    Кто / когда — домашний, ночью, телефон рядом.

    Ситуация. Ночью важно не «всё время видеть график», а получить сообщение в трёх случаях: этап закончился, датчик отказал, превышен лимит стабилизации. И не получать сообщений об остальном.

    Ход. 1. Фоновый цикл: опрос телеметрии SSVC_POLL_HZ (1 Гц), сравнение снимка с предыдущим. 2. На event или смену type — уведомление нужного уровня: - heads_finished / late_heads_finished / hearts_finished / tails_finished — «этап завершён»; - ds_error — «ошибка датчика»; ds_error_stop — «оборудование отключено по ошибке датчика» (критично: контроллер снял реле через 180 с, если ошибка не ушла); - stabilization_limit — «температура не возвращается, лимит стабилизации превышен». 3. Эскалация: при критическом событии — не только push, но и oc_get_hardware_faults + oc_get_process_status в том же сообщении, чтобы человек не бегал по вкладкам.

    Эффект. Человек спит, но узнаёт о проблеме в ту минуту, когда она возникла. Раньше — только если случайно откроет приложение.

    Требования. API ≥ 1.7; настроенные уведомления (MCP-клиент или OpenConnect → VK/Telegram).

    Ограничения. Доставка push зависит от клиента; сервер гарантирует обнаружение события, а не то, что телефон его покажет.

    C2. «Процесс завис — уже четыре часа одно и то же»

    Кто / когда — оператор, вернулся через несколько часов.

    Ситуация. type не меняется, time растёт, но отбор фактически не идёт: клапан закрыт после остановки по температуре, и возврата нет. Такое бывает при переохлаждении дефлегматора или недостаточной мощности.

    Ход. 1. oc_get_process_status + oc_get_telemetry — stop: 1, stops, preempt_cnt, tp1 против tp1_target. 2. Сервер считает: сколько времени в состоянии stop, как далеко температура от tp1_target. 3. Диагноз словами: «отбор остановлен, температура выше цели на X °C, число стопов N; похоже на …». 4. Предложение действий: поднять мощность/подачу воды, либо oc_next, либо oc_stop.

    Эффект. Пользователь узнаёт о застое через час, а не через сутки, и понимает причину.

    Требования. API ≥ 1.7.

    Ограничения. Сервер не управляет нагревом и водой, поэтому «лечит» только советами и командами контроллера.

    6. Сценарии: настройка параметров

    D1. «Гистерезис и предекремент: не сломать друг друга»

    Кто / когда — оператор, впервые включает предекремент.

    Ситуация. Предекремент заранее снижает скорость отбора, не доводя до остановки. Но у него есть жёсткое условие: он работает только при достаточном гистерезисе.

    Ход. 1. oc_get_settings — текущие hyst, predec, decrement. 2. Сервер проверяет правило: predec = 7 требует hyst ≥ 0.12; predec = 13 требует hyst ≥ 0.18. 3. Если правило нарушено — не отправляет SET, а объясняет: «предекремент будет автоматически отключён контроллером, поднимите гистерезис или уменьшите предекремент». 4. Если всё согласовано — oc_update_settings с обоими полями в одном пакете. 5. Напоминание про «Сдвиг Т.отбора»: при включённом сдвиге (+0.07 °C) гистерезис ставят на 0.07 меньше.

    Эффект. Убирает самую обидную ошибку начинающих: функция включена в интерфейсе, но не работает в контроллере, и человек не понимает почему.

    Требования. predec — API ≥ 1.9. Сдвиг отбора входит в базовый набор 1.7.

    Ограничения. Правила взяты из руководства изготовителя; если прошивка их изменит, сервер должен брать значения из api_features/валидации устройства.

    D2. «Формула или Формула авто 92+?»

    Кто / когда — оператор, подбирающий режим на новом сырье.

    Ситуация. Обычная «Формула» начинает снижать скорость строго с formula_start_temp (по умолчанию 92 °C в кубе), даже если колонна ещё держит максимум. «Формула авто 92+» ждёт ещё и признака подъёма температуры в колонне.

    Ход. 1. oc_get_capabilities — доступна ли formula_auto92 (API ≥ 1.9). 2. oc_get_settings — что включено сейчас (formula: 0 / 1 / 2) и formula_start_temp. 3. Объяснение разницы и цены: «авто 92+» экономит время, но требует включённого предекремента, потому что опирается на его срабатывание. 4. oc_update_settings — включить один из режимов (взаимоисключающе) + согласованные predec/hyst.

    Эффект. Пользователь выбирает режим осознанно, а не «как в видео». На практике это десятки минут на перегоне и меньше остановок.

    Требования. formula = 2 — API ≥ 1.9; на более старых доступно только formula=1.

    Ограничения. Формула не заменяет декремент: они работают совместно, и итоговая скорость — минимум из двух.

    D3. «Сброс и снижение голов» (только 2.3)

    Кто / когда — оператор на прошивке 2.3, хочет ускорить вывод голов, не теряя качество.

    Ситуация. В начале голов концентрация примесей высокая — их можно отбирать быстрее, а к концу скорость нужно снизить, иначе потащит тело.

    Ход. 1. oc_get_capabilities — extended_heads доступна (API ≥ 1.8). 2. oc_get_settings — release_speed, release_timer, heads_final, valve_bw[0]. 3. Расчёт объёма сброса: release_speed / период_голов × valve_bw[0] × release_timer / 3600 — сервер показывает ожидаемый объём в мл, чтобы человек не «сбросил» половину голов в канал. 4. oc_update_settings с extended_heads=1 и тремя параметрами. 5. Проверка, что heads_final меньше периода голов, а release_speed — меньше периода (иначе клапан не закроется и скорость станет 100 %).

    Эффект. Экономия времени на головах без риска «протащить» примеси в тело.

    Требования. Ветка 2.3.x, API ≥ 1.8, заданные valve_bw.

    Ограничения. На 2.2.x параметров нет — сервер отвечает feature_unsupported с пояснением, а не молча игнорирует.

    D4. «Откалибровать пропускную способность клапанов»

    Кто / когда — любой, кто хочет видеть скорость в мл/ч, а не «открыт 2.0 с из 4».

    Ситуация. Пока valve_bw не заданы, все скорости — в относительных единицах. С ними — в мл/ч, и калькулятор может считать объёмы и время.

    Ход. 1. Сервер объясняет измерение: собрать жидкость при полностью открытом клапане за известное время, пересчитать в мл/ч, повторить в реальных условиях (высота, вязкость, температура). 2. oc_get_settings — текущие значения. 3. oc_update_settings с valve_bw=[...] (каждое ≤ 20000 мл/ч). 4. Проверка эффекта: oc_get_telemetry — в телеметрии появляются осмысленные alc, объёмы; в следующих отчётах скорость уже в мл/ч.

    Эффект. Все последующие сценарии (расчёт профиля, оценка «сколько осталось», разбор журнала) становятся количественными, а не «на глаз».

    Требования. API ≥ 1.7.

    Ограничения. Пропускная способность зависит от условий; одно измерение — не истина навсегда.

    D5. «Поправить скорость прямо сейчас, не перезапуская»

    Кто / когда — оператор в середине тела.

    Ситуация. Видно, что отбор идёт быстрее, чем колонна держит: температура ползёт. Или наоборот — явно медленно, время поджимает.

    Ход. 1. oc_get_telemetry — текущие open, period, stop, stops, tp1 против tp1_target. 2. oc_update_settings с оперативными параметрами текущего этапа: s_speed (скорость), s_hyst (гистерезис), s_decrement, s_timer, s_temp. 3. oc_get_telemetry — подтверждение новых значений.

    Эффект. Правка «на ходу» без остановки процесса и без перезаписи постоянных настроек этапа.

    Требования. API ≥ 1.7 (оперативные s_* — базовый набор).

    Ограничения. s_* действуют на текущий этап; после перехода они не сохраняются как постоянные.

    7. Сценарии: профили и калькулятор

    E1. «Профиль из расчёта, а не из головы»

    Кто / когда — домашний впервые и оператор на новом сырье.

    Ситуация. Есть 18 л сырца 40 %, колонна 2 кВт, насадка СПН. Сколько голов, сколько тела, с какой скоростью, сколько это займёт? Считать вручную — полчаса и ошибки.

    Ход. 1. Пользователь даёт входные данные: мощность, объём, крепость, стабилизация, доли фракций. 2. oc_calculate_plan (расчёт без обращения к контроллеру) — сервер считает: общий АС, температуру кипения, объёмы фракций, скорости, длительности, коэффициент паровой нагрузки (КПН), остаток в кубе. 3. Сервер показывает план и его допущения: «КПН тела 3.4 — в норме (2–5); головы 216 мл при 3 % от АС». 4. oc_profile_create — создать профиль с этими параметрами. 5. По желанию — oc_profile_apply.

    Пример расчёта. 18 л × 40 % → 7200 мл абсолютного спирта. Головы 3 % → 216 мл, подголовники 7 % → 504 мл, тело 75 % → 5400 мл, хвосты 5 % → 360 мл. Это те числа, которые человек иначе считает калькулятором вручную.

    Эффект. Профиль перестаёт быть набором угаданных цифр. Плюс сразу видно, укладывается ли процесс в ночь: расчётное общее время против available.

    Требования. Расчёт — только сервер; для применения — API ≥ 1.7 и заданные valve_bw.

    Ограничения. Расчёт идеализирован: не учитывает теплопотери, качество насадки, реальную мощность. Он даёт порядок величин и согласованность параметров, а не гарантию.

    E2. «Профиль и контроллер разошлись»

    Кто / когда — оператор, вернулся к установке после того, как кто-то «покрутил кнопки».

    Ситуация. На контроллере правили настройки вручную (например, подняли скорость тела). Профиль в OpenConnect остался прежним. При следующем применении профиля правки молча исчезнут.

    Ход. 1. oc_get_telemetry — флаг cfg_chgd (настройки менялись кнопками). 2. oc_get_settings — перечитать фактические значения. 3. oc_profile_get — содержимое профиля. 4. Сервер строит diff по слою SSVC и показывает, что разошлось: «в профиле hearts=[2.5,5], на контроллере [3.2,5]». 5. Решение пользователя: oc_profile_save_current (сохранить факт в профиль) или oc_profile_apply (вернуть профиль на контроллер).

    Эффект. Правки, сделанные руками у колонны, не теряются; расхождение видно до запуска, а не после испорченного перегона.

    Требования. cfg_chgd — API ≥ 1.7.

    Ограничения. Diff строится по полям ssvcSettings; поля профиля, не относящиеся к контроллеру (аналитика, правила реле), сравниваются отдельно.

    E3. «Профиль на другой аппарат»

    Кто / когда — оператор, у которого две установки или который делится режимом с товарищем.

    Ситуация. Профиль проверен на одной колонне; нужно перенести на другую, с другими клапанами и мощностью.

    Ход. 1. oc_profiles_list + oc_profile_get — взять исходный профиль. 2. oc_calculate_plan — пересчитать под новые мощность/объём (скорости и таймеры изменятся). 3. oc_profile_copy — копия с новым именем. 4. oc_profile_update_content — записать пересчитанные значения. 5. oc_profile_apply — применить (с подтверждением).

    Эффект. Перенос — это пересчёт, а не копирование цифр, которые на другом железе значат другое.

    Требования. API ≥ 1.7.

    Ограничения. Профиль не содержит физики аппарата; сервер не знает реальную разделяющую способность.

    8. Сценарии: разбор после процесса

    F1. «Что было ночью?»

    Кто / когда — домашний, утром.

    Ситуация. Процесс закончился, но непонятно: были ли остановки, сколько, на каком этапе, не ушло ли что-то не так.

    Ход. 1. oc_logs_list — список журналов, взять последний process_id. 2. oc_logs_download — скачать CSV в файл (в контекст модели он не попадает целиком). 3. oc_logs_analyze — разбор: по этапам, число остановок и упреждений, суммарное время в остановке, диапазон температур, спиртуозность в начале и конце тела. 4. Короткая сводка словами + 3–5 самых показательных строк.

    Эффект. Вместо «открыл CSV в Excel и глазами искал аномалии» — готовый вывод за минуту. Особенно важно ночью: журнал пишется раз в минуту и в моменты событий (стоп, упреждение, возврат), поэтому все ключевые моменты в файле есть.

    Требования. Команда GET_LOG — API ≥ 1.10. На более старых — feature_unsupported с подсказкой.

    Ограничения. Журнал не содержит причин событий — только факты (стоп, температура, скорость). Интерпретация остаётся за человеком.

    F2. «План против факта»

    Кто / когда — оператор, после каждого перегона.

    Ситуация. Расчёт обещал одно, реальность дала другое. Важно понять, где расхождение: в расчёте, в настройках или в физике колонны.

    Ход. 1. oc_profile_get — расчётная аналитика профиля (таймеры, объёмы, скорости). 2. oc_logs_download + oc_logs_analyze — фактические: длительность этапов, объёмы по v1/v2/v3, число остановок. 3. Сопоставление по этапам: где именно разошлось и насколько. 4. Вывод: «тело шло на 40 % дольше расчёта при 6 остановках — вероятно, занижена мощность или завышена начальная скорость».

    Эффект. Появляется обратная связь: профиль улучшается от перегона к перегону, а не остаётся застывшим.

    Требования. API ≥ 1.10 для журнала; расчёт — на сервере.

    Ограничения. Сравнение корректно, только если профиль не менялся по ходу процесса.

    F3. «Накопить статистику по сырью»

    Кто / когда — оператор, ведёт журнал по разным партиям.

    Ситуация. Одно и то же сырьё ведёт себя по-разному. Хочется понять закономерность и подобрать стартовую скорость тела.

    Ход. 1. oc_logs_list → oc_logs_download для нескольких процессов. 2. oc_logs_analyze по каждому → нормализованная сводка (этап, время, остановки, температуры). 3. Сведение: таблица «партия → параметры → результат». 4. Рекомендация по стартовой скорости для следующего раза.

    Эффект. Опыт перестаёт быть «в голове»: есть данные, на которые можно опереться. Изготовитель прямо пишет, что журнал полезен для подбора оптимальной начальной скорости на одном и том же сырье.

    Требования. API ≥ 1.10.

    Ограничения. Нужны однотипные постановки (та же колонна, та же мощность), иначе сравнение бессмысленно.

    9. Сценарии: безопасность, датчики, реле

    G1. «Датчики уровня не дают стартовать»

    Кто / когда — домашний, купил датчики XKC-25, но старт блокируется.

    Ситуация. В режиме block контроллер не запускает процесс при некалиброванных датчиках. Это правильно, но пользователю непонятно, что делать.

    Ход. 1. oc_get_xkc25_status — start_guard_mode, block_start, block_reasons, состояние каждого слота. 2. Сервер переводит причины в действия: «датчик 2 не калиброван → выполнить калибровку». 3. oc_xkc25_calibrate шаг without_liquid → with_liquid → (опционально) verify_return с ожиданием oc_xkc25_verify_status. 4. Повторная проверка: block_start: false.

    Эффект. Блокировка перестаёт быть препятствием и становится подсказкой.

    Требования. Подсистема XKC-25 включена; после изменения конфигурации может требоваться перезагрузка.

    Ограничения. Если датчик нестабилен (unstable_signal, not_reacted), сервер честно скажет, что калибровка не прошла, и предложит проверить монтаж, а не будет «дожимать» шаги.

    G2. «Тревоги по температуре приёмных ёмкостей»

    Кто / когда — любой, у кого есть датчики в ёмкостях.

    Ситуация. Порогов три уровня (min, dangerous, critical), и их нужно согласовать с реальностью, а не оставить заводские 80/100.

    Ход. 1. oc_get_alarms + oc_get_sensors — какие датчики есть, какие пороги стоят. 2. Обсуждение с пользователем: что для этой ёмкости «опасно». 3. oc_set_alarm_thresholds — точечно по адресам. 4. Проверка: oc_get_alarms — перечитанные значения.

    Эффект. Тревоги перестают «орать зря» или, наоборот, молчать до аварии.

    Требования. Датчики в зонах, admin-доступ, P2.

    Ограничения. Пороги — это сигнализация, а не автоматика: сами по себе они ничего не отключают.

    G3. «Реле: включить вентиляцию по стадии и выключить при аварии»

    Кто / когда — оператор с расширителем PCF8574.

    Ситуация. Хочется, чтобы вытяжка включалась на этапе тела, а при аппаратном сбое — включалась аварийная сигнализация.

    Ход. 1. oc_get_relay_metadata — какие линии доступны (editable), какие зарезервированы под аварии. 2. Правило в профиле: условие rectification со stageEquals: hearts → линия N, actionEnergize: true; отдельно условие hardware_fault → линия M. 3. oc_profile_update_content — сохранить правила в профиль, oc_profile_apply — применить. 4. Проверка oc_get_relay_state — битовые маски. 5. Ручная проверка конкретной линии: oc_relay_override с явными enable и energized.

    Эффект. Автоматика покрывает то, чего нет в контроллере SSVC: вентиляцию, свет, сигнализацию.

    Требования. PCF8574-сборка (PINOUT_USE_GPIO=0), P2. На GPIO-сборке — feature_unsupported.

    Ограничения. Реле не управляет нагревом и клапанами отбора: это отдельная линия, не замена SSVC.

    10. Сценарии: диагностика

    H1. «Шина I²C подозрительно молчит»

    Кто / когда — поддержка или оператор после «странных» показаний.

    Ситуация. Датчики то есть, то нет; дисплей мигает. Классика: просадка питания, плохой контакт, обрыв на линии.

    Ход. 1. oc_get_hardware_faults — коды (i2c_nack, i2c_bus_down, device_not_present), адреса, роли, i2c_scan — кто реально ответил. 2. oc_get_hardware_config — адреса устройств, результаты проб (bmp581ProbeOk, ds3231ProbeOk…). 3. Вывод: «адрес 0x27 (дисплей) не отвечает, остальные на месте — проблема в конкретном модуле, не в шине».

    Эффект. Пользователь не разбирает всю установку, а идёт к конкретному разъёму. Поддержка не едет на объект ради «посмотрите, что там».

    Требования. P2.

    Ограничения. Проба I²C подтверждает только факт ответа, не качество связи.

    H2. «Настройки не применились»

    Кто / когда — любой после сохранения.

    Ситуация. Интерфейс сказал «сохранено», а контроллер работает по-старому. Причин три: поле не поддерживается версией API (skipped), поле неизвестно прошивке (ignored), пакет не встал в очередь (partial).

    Ход. 1. Сервер разбирает ответ PUT /rest/settings: accepted, ignored, skipped, partial. 2. oc_get_settings — перечитать фактические значения. 3. Объяснение: «predec пропущен: требуется API 1.9, устройство сообщает 1.7». 4. При partial_apply — никакого автоматического повтора; только перечитывание и решение.

    Эффект. «Сохранено» перестаёт быть ложью. Человек видит, что именно не доехало и почему.

    Требования. API ≥ 1.7.

    Ограничения. Часть полей может применяться асинхронно (через очередь команд), поэтому перечитывание делается с небольшой паузой.

    H3. «Журнал не скачивается»

    Кто / когда — оператор после первого включения журналов.

    Ситуация. Три типовые причины: старая прошивка (нет GET_LOG), занятая сессия передачи (log_transfer_busy), нехватка памяти на контроллере (log_heap_low).

    Ход. 1. oc_get_capabilities — есть ли get_log (API ≥ 1.10). 2. oc_logs_list — статус сессии; при busy — сообщить «идёт другая передача», а не ретраить вслепую. 3. oc_logs_download — при 503 log_heap_low объяснить причину и предложить повторить позже или освободить память контроллера.

    Эффект. Вместо «не работает» — конкретная причина и что делать.

    Требования. API ≥ 1.10.

    Ограничения. Сервер не может «ускорить» передачу: скорость задаёт контроллер.

    11. Сценарии: интеграции и мелочи с эффектом

    I1. «Уведомления туда, где я их увижу»

    Кто / когда — домашний, который не сидит в веб-интерфейсе.

    Ситуация. OpenConnect умеет Telegram и VK, но по умолчанию выключен.

    Ход. 1. oc_get_subsystems — состояние telegram_bot, vk_bot. 2. oc_set_subsystem (enabled: true) — включить (таймаут до 120 с: подсистема поднимается долго). 3. Проверка: oc_get_subsystems снова.

    Эффект. События процесса приходят в мессенджер, а не «куда-то в приложение».

    Требования. P2; настроенные токены в OpenConnect.

    Ограничения. Доставка — на стороне OpenConnect и мессенджера.

    I2. «Отдать телеметрию в умный дом»

    Кто / когда — оператор с Home Assistant.

    Ситуация. Хочется видеть стадию и температуры на общем дашборде, рядом с остальными приборами.

    Ход. 1. oc_get_subsystems — включён ли MQTT. 2. oc_set_subsystem при необходимости. 3. Проверка топиков: openconnect/telemetry, openconnect/sensor/state.

    Эффект. Ректификация встроена в общий дом, без отдельного приложения.

    Требования. P2; настроенный брокер.

    Ограничения. MQTT публикует состояние, но не заменяет журналы и профили.

    J1. «Показать адрес сервера на экране контроллера»

    Кто / когда — поддержка при настройке чужой установки.

    Ситуация. Нужно, чтобы человек у колонны видел, куда подключаться, не открывая телефон.

    Ход. 1. oc_send_command с command: status, parameters: "MCP 192.168.1.10" (строка до 15 символов). 2. Контроллер показывает строку на дежурном экране.

    Эффект. Мелочь, которая экономит звонок: адрес виден на самом устройстве.

    Требования. API ≥ 1.7; контроллер в дежурном режиме.

    Ограничения. Строка перезаписывается следующей командой STATUS.

    13. Сквозной сценарий: один вечер

    Чтобы увидеть систему целиком — как её пройдёт домашний пользователь.

    1. 18:40. Проверка. A1: сбоев нет, датчики на месте, датчик уровня калиброван.
    2. 18:45. План. E1: 18 л × 40 % → 7200 мл АС; головы 216 мл, подголовники 504 мл, тело 5400 мл. Расчётное время ~7 ч 20 мин. КПН тела 3.4 — в норме.
    3. 18:50. Профиль. E1: профиль создан и применён. E2: расхождений с контроллером нет.
    4. 18:55. Правка под сегодняшнее сырьё. D5/D1: hearts_finish_temp 93.0, hyst 0.19, predec 13 (правило 0.19 ≥ 0.18 соблюдено).
    5. 19:00. Старт. B1: start → tp1_waiting → delayed_start (отсрочка 20 мин) → heads.
    6. 23:30. Головы закончились. C1: уведомление heads_finished; контроллер по auto_mode переходит к подголовникам, затем к телу.
    7. 02:10. Стоп по температуре. C1/C2: stop: 1, predec сработал 3 раза; сообщение «тело идёт с упреждениями, скорость снижена автоматически» — вмешательство не нужно.
    8. 08:15. Финал. C1: hearts_finished. B4 не понадобился.
    9. 08:20. Разбор. F1: журнал скачан, 2 остановки, 3 упреждения, суммарно 46 мин в остановке. F2: тело шло на 12 % дольше расчёта — в пределах нормы для этого сырца.
    10. 08:30. Итог. E2: правки, сделанные ночью кнопками (если были), зафиксированы в профиль oc_profile_save_current.

    Эффект вечера: пользователь спал, знал о каждом значимом событии, утром получил разбор и улучшенный профиль. Ни одного ручного curl, ни одной поездки к колонне.

    14. Антисценарии: чего сервер не делает

    Это так же важно, как список возможностей: именно здесь пользователь теряет доверие, если ожидания не совпадут.

    Не делает Почему
    Не «ведёт» ректификацию автономно решение о переходе фракции — за человеком; сервер даёт наблюдение и команды
    Не обходит предохранители (XKC-25, guard старта) это защита оборудования и продукта
    Не повторяет PUT /rest/settings при partial часть настроек уже применена, повтор исказит состояние
    Не ретраит POST команды команда не идемпотентна
    Не меняет hyst/decrement «наугад» без запроса это вмешательство в качество продукта
    Не управляет нагревом, водой, давлением вне зоны контроллера SSVC и OpenConnect
    Не гарантирует доставку push зависит от клиента и мессенджера
    Не выдаёт «сертификат качества» спирта расчёты косвенные, лабораторный анализ не заменяются
    Не работает с двумя контроллерами одновременно решение v1: один контроллер

    15. Известные расхождения документации

    Пригодится и пользователям, и разработчикам: там, где источники не согласны, сервер должен опираться на валидацию устройства, а не на документ.

    Параметр API-документация Руководство 2.2.55 Руководство 2.3.28 Как поступать
    hyst не более 50.0 0.06…5.0 0.06…2.0 доверять ответу устройства; предупреждать о диапазоне руководства
    late_heads_timer до 86400 с, кратно 300 — 0…240 мин доверять устройству
    release_timer до 1200 с — до 20 мин согласовано
    Версия API в README 1.9 — — прошивка OpenConnect целится в 1.10 (GET_LOG)

    16. Как проверять сценарии

    Сценарии не нужно проверять все сразу. Порядок — по приоритету и по готовности пакетов.

    Этап Сценарии Критерий приёмки
    после WP0–WP1 A3, C2, H2 (частично) отчёт формируется, ошибки понятны, нет ложных «всё хорошо»
    после WP2 A2, B4, J1 «почему не стартует» закрывается одним вызовом; аварийная остановка срабатывает без подтверждения
    после WP3 D1, D2, D5, H2 правило predec/hyst не даёт отправить заведомо нерабочую пару; partial не повторяется
    после WP4–WP6 A1, G1, G2, H1 причины блокировки старта переводятся в действия
    после WP7–WP8 E1, E2, F1, F2 diff профиля и разбор журнала дают вывод, а не дамп данных

    Метрики полезности (по ним видно, что сценарий действительно нужен):

    • время до ответа: «почему не стартует» — меньше минуты вместо переписки с поддержкой;
    • предотвращённые потери: несохранённые правки (E2), испорченная фракция (D3), ночной застой (C2);
    • сокращение цикла: разбор журнала — минуты вместо ручного Excel (F1);
    • снижение обращений: A2, A3, H1, H2 закрывают типовые вопросы без человека.

    17. Что нужно добавить в каталог инструментов

    Три сценария потребовали инструментов, которых нет в базовом каталоге. Их стоит добавить отдельным пакетом (расчёт и разбор — чистые функции, без обращения к контроллеру):

    Инструмент Риск Назначение Сценарии
    oc_calculate_plan 0 расчёт процесса по входным данным (мощность, объём, крепость, доли фракций): АС, температуры, объёмы, скорости, таймеры, КПН E1, E3, F2
    oc_logs_analyze 0 разбор скачанного CSV: события, остановки, упреждения, время по этапам, температуры F1, F2, F3
    oc_profile_diff 0 сравнение профиля с фактическими настройками контроллера E2

    Первые два — перенос уже существующей логики OpenConnect (DistillationCycleModel и разбор журнала) на сторону сервера; они не требуют новых данных с устройства.

    18. Итог

    Каталог даёт 29 сценариев в девяти группах: от «готов ли контроллер» до «что было ночью». Три из них закрываются в первом же работающем варианте и снимают основную массу вопросов; остальные добавляются вместе с пакетами работ.

    Главная мысль, которая проходит через все сценарии: сервер ценен не тем, что «умеет вызывать REST», а тем, что переводит состояние контроллера в понятное действие и понятный вывод — с учётом ветки прошивки, ограничений параметров и реальной физики процесса.
